# P→D 側の界面 run を混合精度とコンパイルで短縮できるか、処方を変えずに実測する

**task_id:** T-2026-09-17-amp-compile-timing  **kind:** impl

## 1. 背景

前契約 `T-2026-09-17-frozen-feature-cache-timing` で、4 時間の原因は凍結塔の再計算ではないと分かった。
1 step 0.4937 秒の内訳は、凍結塔の順伝播が 4.63〜7.68%、残りが FiLM より後段の順伝播と逆伝播である。
キャッシュは上限 1.08 倍にしかならず、実測では I/O 律速で 1.5〜1.8 倍遅くなった。

計算そのものが 99% を占めるなら、次に当たるべきは数値精度と計算グラフの最適化である。
利用者の確認（2026-09-17）により、**現行は単精度（fp32）で回している**。装置は RTX A6000 で、
半精度の演算器を持つ。前契約と同じく、**腕を削らずに済むかを先に測る**。

原因が実装なら実装を直す。実装で足りなければ設定か問いを変える。これは提案関門の失敗時手順の順番である。

**本契約は GPU を使う**（利用者承認済み）。

## 2. 確定した事実（ホストによらない値だけ）

- 前契約の実測（`docs/stage0/C1_frozen_feature_cache_timing.md`）: 1 step 0.4937 秒、
  データ供給 0.51% / 順伝播 62.52% / 逆伝播 36.45% / 最適化 0.52%。1 epoch 4,809 step で 39.6 分、
  val 評価 1,515 枚で 2.2 分、合わせて 41.8 分。6 epoch で 4.18 時間
- 基準 run は `pd_refin_empty_seed42`（索引と証跡から特定済み）。処方・seed・折り・主指標が揃っている
- W1 の学習対象は 266,880 param、W2 は 25,505,568 param。backbone は `freeze_indices=(0,1,2,3)` で
  W1・W2 とも凍結（`…egosurgery_t1b.py` の 42〜43 行付近）
- W2 の 1 step は W1 の 1.205 倍（同一バッチ、n=20 の実測）
- 前契約は `scripts/profile_t1b_step.py` を新設した。step の内訳を測る道具として本契約でも使える
- 前契約はキャッシュの実体を `third_party/Relation-DETR/data/processed/` 配下に落とした。版管理外・同期対象外
- `.venv-relation-detr` は efros で再構築済み。nvcc は 12.9、torch は 2.1.2+cu118。
  **`torch.compile` は 2.1 系では動くが、DETR 系の動的な形に弱い場合がある**。完走しなければその旨を記録する
- preflight の P8 は同 venv に `jsonschema` を要求する。efros では追加導入済み（正本 lock は未変更）
- 対話シェルは zsh。`git --no-pager`。`make` には読み込みを同じ命令に含める

## 3. Task

**コマンドは書かない。実装を読んで決めてよい。** 出力は `audit.md` に残す。

### Task A — 開始状態と基準

1. 作業ツリーの清浄を確かめる。開始前から在る未追跡は移動で退避し、退避先と件数を記録する
2. 装置の状態を記録する。他利用者の処理があれば停止して諮る。**プロセスの計数は `/proc/PID/exe` の解決か
   引数の完全一致で行う。部分一致は使わない**
3. 現行の数値精度を実装から特定する。`autocast`、`GradScaler`、`amp`、`dtype` の指定を探し、
   **行を指して単精度であることを示す**。すでに混合精度が入っていればその旨を記録し、Task B の条件表を見直す
4. 基準の step 時間を同一ホストで取り直す（前契約の 0.4937 秒。同じ道具で再現するか）。
   **前契約の値をそのまま引き継がない。** 差があればその差を記録する
5. 前契約が残した `third_party/Relation-DETR/data/processed/` 配下の大きさをバイト数で測る（丸めを実数として扱わない）
6. `conventions_rev` と `runindex_commit` を実測し spec.yaml の占位を差し替える

### Task B — 条件ごとの step 時間

**測る条件**（実装が受け付けるものだけ。受け付けないものは理由を書いて除く）:

| 条件 | 内容 |
|---|---|
| 基準 | 現行のまま（単精度） |
| 半精度 A | bfloat16 の自動混合精度 |
| 半精度 B | float16 の自動混合精度（勾配の尺度調整を伴う） |
| コンパイル | 計算グラフの最適化のみ（精度は単精度） |
| 併用 | 最良の半精度とコンパイル |

**測り方の要件**:

1. 同一バッチ、同一ホスト、同一時刻帯。他の処理を同時に走らせない
2. **暖機を入れる**（最初の数 step は捨てる。コンパイルは初回に時間がかかるため、その時間は別行に記録する）
3. **装置の同期を取ってから計時する**。取らないと非同期実行で速く見える
4. 短い測定（例: 数十 step）と長い測定（例: 数百 step）の両方で倍率を出し、**一致することを示す**。
   一致しなければ計時が壊れている
5. 記憶領域の使用量も記録する（半精度で減れば、将来バッチを増やす余地になる）
6. W1 と W2 の両方で測る。W2 は学習対象が 95 倍なので効き方が違う可能性がある

数値の異常（発散、非数、損失の跳ね）が出たらその条件は除外し、記録する。

### Task C — 最良条件での折り A 一本

1. Task B の最良条件で、基準と**同じ処方・同じ seed・折り A** の run を一本、6 epoch 回す
2. 主指標を基準の記録と比べる。差を出し、**seed 間の散らばり**（同型 run の σ。`docs/stage0/` か runindex から引く。
   無ければ UNKNOWN と書く）と並べて書く
3. 差が散らばりと同程度以上なら停止して諮る（escalate_if）。**精度を下げて結果が変わるなら、速さの意味が無い**
4. 学習の経過（損失の推移）を基準と並べる。途中で跳ねていないか

時間が足りない場合は 6 epoch を短縮せず、Task B の結果だけで報告してよい（その旨を UNKNOWN に書く）。
**処方を変えて速く見せることはしない。**

### Task D — 計算器への差し戻し

1. `tools/estimate_tier_cost.py` の所要時間表に、本契約の実測を反映した場合の日数を出す。
   単精度の場合と最良条件の場合の両方
2. W2 の代理値 4.00h を前契約の実測比 1.205 から 4.82h に直した場合も併せて出す。
   **表そのものを直してよい**（`docs/stage0/B1_tier1_cost_estimate.md` と計算器が読む表）。直したら
   `--check-doc` が差 0 になることを確かめる
3. 前契約の報告にある「縮退なしで 153.1〜208.7 日」がどの前提で出た数字かを `audit.md` から特定する。
   計算器は同じ前提（K=3、2 枚、24h）で 84.1〜111.9 日を返す。**食い違いの原因を記録する**（起票者の側の
   読み違いなら、そう書いてよい）

## 6. 想定外と停止条件

- 半精度で発散・非数 → その条件を除外して記録。他の条件は続ける
- コンパイルが完走しない → 実装の改変が要るなら停止して諮る。改変なしで回避できるなら記録して続ける
- 主指標の差が散らばりと同程度以上 → 停止して諮る
- 装置が使われている → 停止して諮る
- 短縮が小さい（例: 1.2 倍未満）→ それ自体が結論。停止せず報告する
- すでに混合精度が入っていた → 条件表を見直し、その旨を報告の先頭に書く
