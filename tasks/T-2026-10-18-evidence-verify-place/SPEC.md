# 証拠地図の照合器と様式の検査を repo に置き、地図と元の報告を照合して docs/evidence/ に配置する

**task_id:** T-2026-10-18-evidence-verify-place  **kind:** impl

**本契約では GPU を使用しない。**

## 背景

文献探索の報告から起票者が証拠地図を起こし、機械で照合し、利用者が原典を確かめる、という分担が F 2026-10-03（Notion の知見・決定。本契約が引く値はすべて本書に写してある）で決まっている。同じ決定で、照合は契約ごとに作らず一つの命令にまとめること、元の報告そのものを repo に置くことも決まった。前回の照合（T-2026-09-16-evidence-map-ab）は照合の道具を repo に残していない。

本契約は三つを行う。

1. **道具を置く。** 地図の書誌 ID（DOI と arXiv ID）を一つの命令で照合する照合器と、地図の様式の検査を tools/ に置く。あわせて、契約の追加ファイルの宣言（spec.yaml の inputs.bundle_extras）を spec の schema が受け付けるようにする（下の「環境の罠」の一）
2. **置く。** 起票者が作った地図三件（D→P の地図 C v2、P→D の地図 B v2、新規性の照合の地図 N v1）、地図の雛形、元の報告五件を docs/evidence/ に置く。旧地図 B（2026-09-16）は残し、v1 であることを冒頭に明記する
3. **照合する。** 三つの地図を照合器と様式の検査にかけ、結果を残す。**地図の本文は書き換えない。** 照合で分かった差や欠けをどう地図へ反映するかは、起票者が結果を読んでから決める

この照合が済むまで、地図 C と地図 B を提案カードの生成会話へ渡さない（F 2026-10-03 の手順）。

## 環境の罠（実行者が知り得ないこと）

1. **spec の schema は inputs.bundle_extras を受け付けない。** tools/fetch_task.py は追加ファイルの宣言を読み、要約値まで照合するが、取り込みの最後に呼ぶ make task-validate の L1-1 が `inputs: Additional properties are not allowed ('bundle_extras' was unexpected)` で落ち、取り込みが巻き戻る。起票者が phase0 40112290 の tools/validate_task.py と tasks/_schema/spec.schema.json の写しで validate_l1 を実行して確かめた。docs/stage0/stage0_summary.md は「取り込みの拡張は完了した」と書くが、宣言を使った契約は過去に一件も無い。**本契約で schema を直す**（Task B-3）
2. **起票側から台帳へ大きなファイルを添付する経路が無い。** 起票者の環境は Notion の API に直接届かず、添付は本文をそのまま送る方法に限られる（一件の上限 200 KiB）。本文を送り直すと写し誤りが入りうるため、十件は利用者の手で受け渡す
3. **Zenodo などの DOI は Crossref ではなく DataCite に登録されている。** Crossref だけを引くと、実在する DOI を「不在」と誤る。地図 N の N-01 に `10.5281/zenodo.20086606` がある（報告は Zenodo の record との対応を未確認としている）。不在と判定する前に DOI の登録機関を確かめること
4. **書誌の照合では、複合姓と発音記号を両側で同じに正規化する。** 前回の照合で、Abu Farha と Lüddecke を差と誤検出した（照合器の正規化が片側だけだった。tasks/inbox.d/T-2026-09-16-evidence-map-ab.md）。今回も地図 B に Lüddecke と Gaël Varoquaux がある
5. **arXiv の API と Crossref には問い合わせの間隔の作法がある。** 各サービスの文書を読んで従う。問い合わせに利用者の連絡先（メールアドレスなど）を入れない
6. **地図に同じ ID が複数回現れる。** 照合は ID ごとに一度でよい。地図側の書誌（題名・著者）と比べるときに、どの箇所の記載を使ったかを結果に残す
7. **地図には照合済みの ID と、報告が ID を確定できなかった行がある。** 地図 B の B-01〜B-11 は 2026-09-16 に照合済みだが、本契約では全 ID を照合し直す。ID の無い行（地図 C の C-24、地図 N の N-15 など）は照合の対象外で、件数だけを数える
8. **生成物の再生成と `context-check`・`inbox-check`・`taskindex-check` を本契約の分岐で回さない。** phase0 への統合のたびに自動の PR が作り直す。`make forbidden-check` は使う

## Task

各 Task の手段は実装を読んで決めてよい。決めた手段と理由は audit.md に残す。

### Task A — 起点を確かめる（Phase A）

- A-1. 分岐が `feat/` で始まり、起点が origin/phase0 であることを記録する。起点の commit を記録する
- A-2. 受け渡しの十件を `~/slocal2/m2-incoming/T-2026-10-18-evidence-verify-place/` から読み、要約値とバイト数が上の表と一致することを確かめる。置き場が repo の作業ツリーの外にあること（実体の経路が repo の最上位の下に入らないこと）も確かめる。**一件でも違えば停止する**（G1）。置かれていなければ利用者に伝えて待つ
- A-3. repo に照合の道具が既にあるかを調べる。前回の照合器は残っていない見込みだが、**異質な二つの方法で確かめる**（たとえば経路名での検索と、Crossref・arXiv の API の URL を文字列で探す検索）。見つかれば再利用を検討し、判断を記録する
- A-4. 照合先（Crossref、DOI の登録機関の解決、DataCite、arXiv の API）へ到達できるかを確かめる。**どれにも届かなければ停止する**（G1）
- A-5. 変更前の値を測る。旧地図二件の要約値、`make test` の失敗の集合、全契約の `make task-validate` の結果（契約ごとの成否の集合）

### Task B — 道具を作る（Phase B）

- B-1. **照合器。** 地図の Markdown を入力に、DOI と arXiv ID を抽出し、ID ごとに次の五つのどれかに分類して保存する
  - 実在・書誌一致 / 実在・書誌に差 / 実在・照合不能（地図側に比べられる題名・著者が無い）/ 不在 / 到達不能
  - 照合先が返した題名・著者・年・掲載先（得られたもの）と、DOI の登録機関を記録する
  - 「書誌一致」の判定規則（何を正規化して何を比べるか）は実装を読んで決め、README に書く
  - 掲載先の違いは分類に入れず、参考として別の欄に記録する
  - 結果は機械が読める形と人が読む要約の両方。置き場は docs/evidence/verification/
  - **一つの命令で一つの地図を照合できる**こと。命令の形（make の目標を足すか、tools/ の直接の実行か）は実装を読んで決める
- B-2. **地図の様式の検査。** docs/evidence/ の Markdown のうち、見出しの前の欄に `**種類:**` を持つものを対象に、雛形（受け渡しの evidence-template.md）の「検査が見る項目」を確かめる
  - 見出しの前の五つの欄、種類ごとの必須の節、citation の印の残骸と私用領域の文字、BMP 外の文字、禁止語、元の報告の sha256 が docs/evidence/reports/ の実在のファイルと一致すること
  - **禁止語は規約から読む。写しを持たない**（tools/check_proposal.py が規約から読む方針と同じ。その関数を使ってよい）
  - 雛形の項目と検査の項目が食い違わないことを試験で固定する
  - 雛形・旧地図（`**種類:**` を持たない）は対象外になることを確かめる
- B-3. **spec の schema に inputs.bundle_extras を足す。** tools/fetch_task.py の extras_from_spec が受け付ける形（path・sha256・bytes の一覧）と同じ制約にする。既存の契約はこの欄を持たないので、検証結果は変わらないはず。**変わらないことを A-5 の集合と比べて示す**
- B-4. **試験。** 照合器・様式の検査・schema の試験を tests/ に足す。**ネットワークに依存しない**（HTTP は差し替える）。repo の既存の試験の流儀に合わせる
- B-5. **対照（G2）。** 次がすべて期待どおりになるまで Task C へ進まない
  - 照合器: 実在の Crossref 登録 DOI と実在の arXiv ID が「実在」、実在の DataCite 登録 DOI が「不在」にならない、架空の DOI と架空の arXiv ID が「不在」、到達できない照合先を指したとき「到達不能」になり「不在」と混ざらない。対照に使う実在の ID は地図に載っているものから選んでよい。実際の照合先に問い合わせた結果を audit.md に残す
  - 様式の検査: 違反の無い地図の写しで零件。写しに、(1) citation の印の残骸、(2) 必須の節の削除、(3) 禁止語、(4) 元の報告の sha256 の一文字の変更、を一種ずつ入れると、それぞれ違反として検出される
  - schema: 形の正しい bundle_extras を持つ spec が L1 を通る。sha256 が 64 桁でない宣言、path が経路の規約に合わない宣言を持つ spec が落ちる。fetch_task の取り込みを通した端から端までの確かめ（宣言つきのバンドルが取り込まれ検証を通る、要約値を改変したバンドルが拒まれる）を一つは置く

| d | spec の schema | 形の正しい bundle_extras が L1 を通り、壊れた宣言が落ちる。全契約の検証結果の集合が変更前と同じ | 変更前の schema では同じ形の正しい宣言が L1-1 で落ちることを先に示す（起票者の実測の再現） |
| e | 配置 | 地図三件と雛形が docs/evidence/、報告五件が docs/evidence/reports/ にあり、要約値が表と一致 | 要約値は置いた後のファイルから計算する。受け渡し前の値の写しと比べない |
| f | 旧地図 | 旧地図 B の表題の直後に v1 の一文。削除行零。旧地図 A の要約値が変更前と一致 | 旧地図 B の削除行数は git の行単位の集計で示す。旧地図 A は要約値で示す（表示の属性では足りない） |
| g | README | docs/evidence/README.md に C-4 の項目がある | README に書いた命令を実際に実行した終了コードを記録する |
| h | 試験 | 新しい試験が通る。全試験の失敗の集合が変更前と同じ | 新しい試験がネットワークを使わないことを、ネットワークを断った状態か差し替えの確認で示す。失敗の集合は件数ではなく試験名の集合で比べる |
| i | 照合の結果の要約 | RESULT に地図ごと・分類ごとの件数と D-4 の各点がある | 地図三件の要約値が表の値のままであることを示す（書き換えていない証拠） |
| j | PR | Draft でなく存在し、base は phase0、分岐は feat/ で始まる。forbidden-check の違反が零 | PR の番号と base を GitHub の応答で示す。push しただけの状態を完了と呼ばない |

## 想定外のときの扱い

- 照合先のどれにも届かない → 停止して利用者に諮る（G1）
- 受け渡しの十件のいずれかの要約値が違う → 停止して利用者に諮る（G1）
- 対照が期待どおりにならない → 停止して報告する（G2）
- 抽出した ID の集合が一覧と違う → 一件ずつ理由を記録して利用者に諮る（G3）。照合器と一覧のどちらかを都合よく直さない
- 照合で「書誌に差」「不在」が多数出る → 件数に関わらず止めずに記録する。地図は直さない
- 作業ツリーを別の契約が使っている形跡（抑止の目印が別の契約の所有、他の分岐の未統合の変更）→ 停止して利用者に諮る
- 実行基盤が操作を拒む（家の直下への書き込み、rm など）→ 回避せず利用者に提示して許諾を得る
