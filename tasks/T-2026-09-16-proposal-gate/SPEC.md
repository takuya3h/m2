# 提案関門の規約（proposal_gate）と提案文書の静的検査器を置く

**task_id:** T-2026-09-16-proposal-gate  **kind:** impl

## 1. 背景

契約システムは実行の正しさ（L1〜L3、forbidden-check、spec-check）を検査するが、
「この実験は回す価値があるか」「根拠は文献にあるか」を問う関門が無い。
メンターから、手法の試し方が雑（失敗時の修正が軽微、試す価値のないものを大げさに推奨）と
指摘があり、これは AI に実験計画を考えさせるときの特徴だと言われた。

対処として、提案を契約に落とす前の関門を規約と文書と検査器で置く。
規約は `context/conventions.md` に `proposal_gate` 節として足し、逐語注入で契約へ渡せるようにする。
手順の全文は `docs/proposal-gate.md` に置く。禁止語と提案カードの充足は機械で検査する。

**本契約では GPU を使用しない。**

## 2. 確定した事実（ホストによらない値だけ）

- 逐語注入のアンカーは `[a-z0-9_]` のみ。ハイフンは L1 と L2 の両方で落ちる
- `context/conventions.md` の変更履歴の表は `naming` 節の本文の内側にある。変更履歴に行を足すと
  `naming` の解決結果が変わり、`naming` を注入する既存契約で L2-6 が WARN になる。これは想定内で、
  FAIL ではない。WARN が出る契約を一件、報告に残すこと（完了判定 e）
- `tools/check_spec.py` の規則は `issuer_defects` の実例を裏付けに持つ設計で、裏付けの無い規則を足すと
  分母が動く。**本契約は spec-check に規則を足さない。** 検査器は別に置く
- `make forbidden-check` は `origin/phase0` を起点に未追跡も列挙する。開始前から在る未追跡が
  禁止領域にあると通らない。その場合は消さず記録する
- 対話シェルは zsh。履歴を読むときは `git --no-pager`。命令ごとにシェルが新しくなる実装系があるため、
  仮想環境の読み込みは同じ命令に含める

## 3. Task

### Task C — `docs/proposal-gate.md` を置く

付録 B の本文をそのまま置く。三連バッククォートと山括弧を含めない。

### Task D — 提案文書の検査器を置く

1. 置く場所と名前は実装を読んで決める。`tools/` 配下を第一候補とする。**`tools/check_spec.py` には
   足さない**
2. 検査は二つ。**禁止語の完全一致**（付録 A の一覧を正本とし、検査器が同じ一覧を持つか規約から読む。
   二重に持つなら試験で一致を確かめる）と、**提案カードの見出し十四件の有無**、および
   期待効果量・成功確率・費用の三項目に数字が含まれるか
3. 入力は markdown 一ファイル。出力は検出の一覧と件数。終了コードは検出があれば非零
4. 試験を置く。陽性対照と陰性対照を両方向で置く（完了判定 b、c）
5. 「未踏」「空白」を含むが「空白である理由の仮説」の節がある本文は、検査では**通す**。
   境界の扱いは批判会話に委ねる（付録 B の B.6）

### Task E — 検証と報告

1. L1、L2、`make forbidden-check`、`make spec-check TASK=T-2026-09-16-proposal-gate`、試験
2. 完了判定 a〜g を実測で埋める
3. `RESULT.md`、`result.yaml`（版 3）、`audit.md`、`tasks/inbox.d/T-2026-09-16-proposal-gate.md` を書く
4. commit、push、PR（Draft でない）。分岐名が `feat/proposal-gate` であることを記録する
5. 報告後に `.sync-pause` を**移動**で解除する

## 4. 禁止事項

**禁止は実行者の操作に対するものであり、同期処理による配布を含まない。**

1. `tools/check_spec.py` の規則を増減しない
2. `context/conventions.md` の既存節の本文を変えない（変更履歴の表への一行追加は除く）
3. `context/auto/*` と `tasks/inbox.md` を再生成しない。並行して別契約が走るため、
   統合後に利用者が一台で一度だけ回す
4. `experiments/**`、`data/**`、`runindex/**` に触れない
5. 既存の `tasks/*/` を変えない
6. 開始前から在る未追跡を消さない。退避は移動で行う
7. 外部への送信は `make task-report` 以外の経路で行わない

## 6. 想定外と停止条件

- 既存節を変えずに新節を置けない → 停止して利用者に諮る
- 実行基盤が `tools/` への書き込みや `rm` を拒む → 回避せず提示する
- `make forbidden-check` が開始前からの未追跡で落ちる → 消さず、件数と mtime を記録して続ける
- L2-6 の WARN が本契約自身に出る（起票後に規約が変わった）→ 実測の側を採り、続行を記録する

## 付録 A — `context/conventions.md` に置く節（このまま置く）

    (aタグ) id="proposal_gate"
    ## proposal_gate

    手法・結合・補助信号・修正案の提案は、本節の関門を通ったものだけを契約に落とす。
    関門は四つ。提案カードの充足／禁止語の不在／失敗時手順の履行／引用の照合。

    ### 提案カード（全項目が埋まるまで推奨を書かない）

    | # | 項目 | 空欄を許す条件 |
    |---|---|---|
    | 1 | 問い。yes/no で答えが出る一文 | 許さない |
    | 2 | 最も近い先行研究三件。著者・年・DOI か arXiv ID・設定・報告された効果量 | 三件未満なら「探して見つからなかった」と検索語を書く |
    | 3 | 先行研究がこれをやらなかった／効かなかった理由の推定 | 許さない |
    | 4 | 否定的な先行研究二件（効かなかった、負の転移の報告） | 同上の「探して見つからなかった」 |
    | 5 | 期待効果量（点）。#2 のどの値から外挿したか | 許さない |
    | 6 | 成功確率（主観。0.0 から 1.0） | 許さない |
    | 7 | 成功の閾値（主判定規則で書く） | 許さない |
    | 8 | 失敗の閾値と、失敗時に捨てるもの（案／設計／問い のどれか） | 許さない |
    | 9 | この案を殺せる最安の実験（GPU 一日以内） | 無いなら「無い」と理由 |
    | 10 | 費用（run 本数 × 時間） | 許さない |
    | 11 | この案の結果でどの判断（関門・分岐）が変わるか | 変わらないなら提案しない |
    | 12 | 最も近い既存研究との差分一文 | 許さない |
    | 13 | F の「却下」「予測外れ」と同型でないことの宣言。読んだ行の id | 許さない |
    | 14 | 初回にセットで試す設定の掃引集合。掃引する主要因、固定する交互作用、固定の理由 | 許さない |

    #5 #6 #10 は数値で書く。#10 は #14 の掃引集合全体で見積もる。
    #11 が空なら、新規性の有無によらず提案から外す。

    ### 禁止語（提案と契約の本文。完全一致で検査する）

    最大の新規性／世界初／画期的／有望／筋が良い／本命／未踏／空白／決定的／確実に効く／
    明らかに／大幅／劇的／必ず改善／唯一の

    「未踏」「空白」を使う場合は禁止を解かず、「空白である理由の仮説（技術的困難／価値が無い／偶然）」を
    添えた別の語で書く。形容詞の代わりに #5 #6 #10 の三数値を併記する。

    ### 設定・設計・問いの三水準

    | 水準 | 含むもの | 変えるときの手続き |
    |---|---|---|
    | 設定 | 学習率・epoch・batch・seed、特徴の取り出し層、豊かさ L0 から L3、学習範囲 W1/W2、損失の重み、送り手の掃引点 | 初回の契約に掃引として入れる。後から足さない |
    | 設計 | 界面の型、塔の選択、方向、信号の種類、時間文脈の与え方 | 提案カードを書き直し、批判会話を通す |
    | 問い | どの仮説を測るか、相互改善の定義、論文の段 | 利用者が決める。関門で扱う |

    設定の掃引は初回にセットで試す。主要因は掃引し、交互作用は固定する。
    何を固定したかと理由をカード #14 に書く。掃引集合はカードに書いた時点で固定する
    （最良格子の選定は折り内 val、test は腕ごとに一度。conventions#split の規則に従う）。

    ### 失敗時手順（修正案を書く前に、この順で書く）

    1. 失敗の定義は初回の契約にある閾値による。掃引のどの格子でも閾値に届かなければ、
       その設計の失敗である。格子を足すことは修正ではない
    2. 原因候補を五区分で列挙する。測定器（eval・split・seed）／データ（ラベル・分布）／
       モデル・実装／仮説そのもの／問いの立て方
    3. 区分ごとに識別実験を一つ書く（どの結果が出ればその区分だと分かるか）
    4. 識別実験の結果で修正の水準を決める。測定器・データ・実装が原因なら、それを直して
       同じ設計を測り直す（設計は変えない）。仮説・問いが原因なら、設計か問いを変える
    5. 設定水準の修正は選べない。例外は、初回に入れなかった設定があり、入れなかった理由が
       契約に書いてある場合のみ。その場合も後から足さず、掃引を再設計して一括で出す
    6. 修正案に提案カードを付ける。設計変更一回の費用を #10 に含める

    ### 引用規約

    - DOI か arXiv ID の無い引用は引用として扱わない
    - 引用は機械で存在照合する。照合の出力を証跡に残す
    - 数値つきで引く。「改善した」ではなく「指標・値・表番号・設定」
    - 設定の違い（データセット・タスク粒度・入力）を必ず書く。「文献に数値がある」を「効く」と読み替えない
    - 反証を先に探す。検索語・件数・見つかった否定例を記録する

    ### 役割分離

    | 役割 | 会話 | 出力 | 禁止 |
    |---|---|---|---|
    | 生成 | 別会話。証拠地図だけを渡す | 提案カード三から五案。互いに排他的な方向 | 推奨・順位。repo の現状を見ること |
    | 批判 | 別会話。カードだけを渡す | 却下表と順位。順位は期待情報量（#11）で付ける | 生成側の推奨文を読む |
    | 判定 | 利用者 | 決定。F に一行 | — |
    | 起票 | 別会話 | 契約 | 手法の変更 |

    生成と批判を同じ会話で行わない。批判は「やらない理由」から書く。

## 付録 B — `docs/proposal-gate.md` の本文（このまま置く）

    # 提案関門（proposal gate）

    対象: 手法・結合・補助信号の「何を試すか」の提案と、失敗時の修正案。
    規約の正本は `context/conventions.md` の `proposal_gate` 節。本文書は手順と根拠。

    ## B.1 なぜ要るか

    契約システムは実行の正しさを検査するが、実験の価値を検査しない。
    実際に起きた提案の欠陥は三型で、いずれも実行の検査では捕まらない。

    | 型 | 実例 | 起きた日 |
    |---|---|---|
    | 大げさな推奨 | 仮説 H-C を「最大の新規性。世界的にほぼ未開拓」と書いた。効果量の見積もりも先行研究の実測値も無い | 2026-06-14 |
    | 軽微な修正 | 凍結／fine-tune の交絡を見つけたとき、設計を疑わず S0-frozen を分母に足した。土台の artifact が主張を反転させると分かったのは 08-26 の再検査。設計の転換は中間審査の指摘後 | 2026-06-02 から 08-28 |
    | 測らずに断定 | 起票者欠陥八件のうち五件が asserted_without_measuring | 2026-08-29 から 30 |

    メンターの指摘（2026-09、口頭）: 手法の試し方が雑。失敗時の修正が軽微。試す価値のないものを
    大げさに推奨する。AI に実験計画を考えさせるときの特徴。

    ## B.2 AI 提案者の癖（抑える対象）

    | 癖 | 現れ方 | 抑える仕組み |
    |---|---|---|
    | 既存物への係留 | いまある分母・コードに足す修正を選ぶ | 三水準と失敗時手順。生成会話に repo を見せない |
    | 同意への偏り | 「やめる」「筋が悪い」を言わない | 批判役の分離。「やらない理由」から書く |
    | 新規性の水増し | 分類表の空白を未踏と呼ぶ | 禁止語。空白の理由の仮説 |
    | 効果量の不在 | 効くはず、と書く | カード #5 #6 #10 の数値 |
    | 失敗の記憶が薄い | 次の起票で同型を繰り返す | カード #13。F の却下・予測外れ行 |
    | 引用の捏造・切り取り | 存在しない文献、都合の良い数値 | DOI 照合。反証の先行探索 |

    ## B.3 問いから契約までの流れ

        利用者が問いを出す
          → 問いの分解（機構の系統、送り手の信号、受け取り手）
          → 文献探索（deep research を二エンジン）→ 起票者が証拠地図の下書き
          → CLI が DOI を全件照合し docs/evidence/ に地図を置く
          → 利用者が設定距離 0 から 1 の論文を二から三本読む
          → 生成会話: 地図だけから提案カード三から五案
          → 批判会話: 却下表と順位
          → 利用者が決定。F に決定行
          → 起票会話: 契約。手法は変えない
          → 実行・報告。カード #5 #6 の予測と実測を突き合わせ、F に予測外れ行

    会話の題名に役割を付ける（例: gen 2026-09-16 補助信号、crit 同）。
    批判会話へ渡すのはカードの本文だけ。生成会話の地の文は渡さない。

    ## B.4 順位の付け方

    順位は「結果がどちらに転んでも次の判断が変わる度合い」で付ける。新しさ・派手さでは付けない。
    判断が変わらない案は、順位を付けずに外す。同順位なら費用が小さい方、次に殺せる最安の実験がある方を上に。

    ## B.5 較正の記録

    カード #6 の成功確率と実測の結果を F に残す。件数が溜まったら Brier スコアで較正を見る。
    2026-08-26 の再検査では過去の結論に「裏付けあり零件」が出たが、各結論の自信は記録されていなかった。

    ## B.6 静的検査

    禁止語とカード充足は機械で検査する。検査器は `tools/check_spec.py` の規則に足さず別に置く
    （spec-check の規則は issuer_defects の実例を裏付けに持つ設計で、分母を動かさないため）。
    対照は両方向。陽性: 禁止語一語で検出一件。陰性: 禁止語なしで零件。
    境界: 「未踏」を含むが「空白である理由の仮説」の節がある本文は、検査では通し、批判会話で見る。
    カード充足は見出し十四件の有無と、#5 #6 #10 に数字が含まれるかまで。内容の妥当性は批判会話が見る。

    ## B.7 修正の大きさは意志ではなく原因で決める

    利用者の方針: 「設定をちょっと変える」程度の修正はしない。設定の変更は初回にセットで試し、
    失敗したら設計か問いを変える。ただし大きく変える側にも失敗の型がある。原因が測定器や実装だったのに
    設計を捨てると、健全な設計を誤って失う。そのため五区分の識別実験を残し、設計変更へ進めるのは
    原因が仮説か問いに絞れたときだけとする。設計変更の回数は締切に制約される。
    G0 の試算に「設計変更一回の費用」を含めること。

    ## B.8 失敗時手順の例（2026-06-02 の交絡発見に当てはめる）

    | 段階 | 当時 | 手順に従うと |
    |---|---|---|
    | 原因の区分 | 書いていない | 測定器（分母の交絡）が第一候補。仮説（共有土台で相互改善を測れるか）が第二候補 |
    | 識別実験 | 無し | 凍結源を替えて符号が変わるかを見る（後に 08-26 でこれが反転を検出した） |
    | 修正の水準 | 設定修正（S0-frozen 追加）のみ | 識別実験が「測定器」を示すなら分母を直して同じ設計で測り直す。「仮説」を示すなら設計を変える（二塔化）か問いを変える |
    | 設定修正の可否 | 設定修正で済ませた | 初回に凍結源の掃引が無く、無かった理由も無いので、設定水準の修正は選べない |
