# 入力側の雑音除去が本番の受容野で効かないことの反証テストと環境の棚卸し

**task_id:** T-2026-08-26-denoise-falsification  **kind:** exp  **server:** andrew

## 0. 最初に読むこと

**本契約の成果は、配布からおよそ 24 時間後の進捗報告会で使われる。**

実行に使ってよいのは **Phase A の開始から 14 時間まで**である。
**Phase A を始める前に時刻を記録し、各 Phase の入口で経過を確かめること。**

**本契約は当該ホストの GPU を使用する。** 他の利用者と競合した場合は止めて報告する。

**本契約は他の四台と同時に走っている。** 生成物の再生成は禁じている（第 5 節）。

### 0.1 このホストで環境が揃っていない可能性が高い

**起票者は当該ホストの状態を知らない。**

横断索引の実測では、**このホストに紐づく run は三件しかない。**
他のホストは四百件を超えるものもある。**環境、データ、重みが揃っていない可能性が高い。**

**そのため本契約は、Phase A を独立した成果物として設計してある。**

**環境が揃っていないと判明しても、それは失敗ではない。**
**何が足りないかが分かること自体が、本契約の成果である。**
そこで止めて、棚卸しの結果を報告すればよい。

## 1. 背景

術具存在の信号を入力側で雑音除去する介入について、次が観測されている。

**代理モデルの上では、分節の指標を一貫して改善した。**
複数の分割、複数の凍結源にわたって、改善の向きが揃っていた。

**しかし、per フレームの分類器に八フレーム分の文脈を与えるだけで、この改善が消えた。**
同時に、雑音除去をしない信号のままでも分節の指標が上がった。
**時系列のモデルが、ちらつきを自力で吸収していると読める。**

**本番の時系列モデルの受容野は、その十六倍にあたる。**
**したがって本番ではほぼ効かないと予測される。**

**この予測は、まだ本番で確かめられていない。**

### 1.1 これは「効かないことを確かめて閉じる」実験である

**成功とは、効かないことが示されることである。**

**ただし、決定的に重要な区別がある。**

**効果が見えないことと、効果が無いことは別である。**

本数が少なければ、実在する小さな効果も見えない。
**したがって本契約が示せるのは「この本数で見える大きさより小さい」という事実だけである。**

**「効果が無いと証明した」と書いてはならない。**

同じ一連の調査の中で、まさにこの区別を明示して次へ引き継いだ前例がある。
**本契約も同じ規律に従う。**

### 1.2 反証テストには陽性対照が要る

**効果が見えなかったとき、次の二つを区別できなければならない。**

- 雑音除去は働いたが、時系列のモデルが吸収したので効果が出なかった
- **雑音除去がそもそも信号を変えていなかったので、何も起きなかった**

**後者であれば、何も測っていないのと同じである。**

**したがって Phase B で、雑音除去が信号を実際に変えていることを確かめる。**
**これを飛ばして対測定へ入ってはならない。**

## 2. 手順

### Task 1 — 開始の記録

**Step 1.** 現在時刻を記録する。

**Step 2.** 作業ツリーの状態を確かめる。**汚れていれば退避してから進む。**
**退避には本契約の識別子を含む名前を付けること。** 退避したことを報告に残す。
**戻すのは契約が終わり、元の分岐へ戻ってからである。本契約の中で戻さない。**

**Step 3.** 抑止の目印を置く。**報告を終えたら移動によって解除する。**

### Task 2 — Phase A 環境の棚卸し（GPU 不要）

**この Phase は独立した成果物である。丁寧に行うこと。**

**Step 1.** 後続に必要なものを、**一つずつ実在を確かめる。**
何が要るかは実装を読んで決めてよい。少なくとも次が要るはずである。

- 仮想環境と、そこに導入されている道具
- 時系列モデルの学習と評価の入口
- 凍結源となる検出器の重み、およびその要約値
- 術具存在の信号
- 雑音除去の実装
- 分割の定義
- 計算資源が使える状態にあること

**Step 2.** **実在するものと、欠けているものを一覧にする。**

**Step 3.** 欠けているものについて、**何があれば後続が走るかを記録する。**
他のホストから運べるものか、作り直せるものか、作り直しに何が要るか。
**これが本 Phase の主たる価値である。**

**Step 4.** 一致が零件だった場合は探し方を疑う。
対象が存在しないのか、条件に合わないのか、対象の集合を間違えているのかを区別する。
**異質な方法で二度確かめる。** 同じ仕組みに依存する二つの方法は同質である。
**先頭がドットのものを含めること。**

**Step 5.** 契約の欄のうち、起票者が埋められなかった二つを実測で差し替える。
差し替えた値を報告に残す。

**判定 G1** — 後続に必要なものがすべて実在したか。
**欠けていれば、棚卸しの結果を成果として報告し、そこで止める。**

### Task 3 — Phase B 雑音除去が信号を変えていることの確認（GPU 不要）

**Step 1.** 雑音除去を施す前と後で、**信号がどれだけ変わったかを実測する。**

変化の量としては、値が変わったフレームの数や、
信号が向きを変える回数の減り方などが考えられる。**実装を読んで決めてよい。**

**Step 2.** 対照を両方向で設置する。

- **陽性対照** — 雑音除去を施した信号は、施す前と**違っているはずである。**
  違っていなければ、雑音除去は働いていない。
- **陰性対照** — 雑音除去を施さない腕の信号は、元の信号と**一致するはずである。**
  一致しなければ、意図しない加工が入っている。

**片方向だけでは、常に何もしない実装と区別できない。**

**Step 3.** 変化の量は**集合の差で求めること。部分一致で数えてはならない。**
件数が合っていることは、入れ替わりが起きていないことを意味しない。

**判定 G2** — 雑音除去が信号を実際に変えていたか。
**変えていなければ、そこで止めて報告する。** 何を測っても効果は出ない。

### Task 4 — Phase C 所要時間の実測と本数の決定

**起票者は本番規模の所要時間を知らない。** 既存の run に所要時間が残っていないためである。
**したがって実測してから決める。**

**Step 1.** 学習を一本走らせ、**所要時間を実測する。**

**Step 2.** 実測した所要時間と経過時間から、**残り時間で対が何組入るかを計算する。**
計算の過程を記録すること。

**Step 3.** **この本数で見える効果の大きさの下限を求める。**
**これは本契約の主たる成果の一つである。**

効果が見えなかったと報告するとき、読む側が知りたいのは
**「どれだけ小さい効果まで見えたのか」**である。
**本数だけを書いても、それは伝わらない。**

**Step 4.** 対が一組も入らない場合は、**Phase D へ入らない。**
棚卸しと信号の確認までで報告する。

**判定 G3** — 残り時間で対が入る見込みがあるか。

### Task 5 — Phase D 対測定

**Step 1.** 雑音除去を施す腕と施さない腕を対にして走らせる。

**Step 2.** **対の両側は種ごとに隣接して交互に走らせること。**
実行の並びが対の揺らぎを大きく変えることが実測されている。**桁が変わる。**
**実際に走らせた順序を記録する。**

**Step 3.** 各対の入口で経過時間を確かめる。
残り時間で**その対の両側**が入らないなら、**その対を始めない。**
**片側だけの腕を作らない。**

**判定 G4** — 対の両側が同数そろい、順序が記録されたか。

### Task 6 — Phase E 報告

**Step 1.** 効果量と、**改善側へ倒れた対の個数**の双方を出す。

**Step 2.** **判定を行わない。** 判定則は別のホストで走っている契約が確定させる。

**Step 3.** **効果が見えなかった場合、効果が無いとは書かない。**
**「この本数で見える大きさより小さい」と書く。**
**Phase C Step 3 で求めた下限を添えること。**

**Step 4.** 変更範囲の一覧を出す。

**Step 5.** 完了報告を**二つに分ける。**

- 事実の記録 — 判定、完了判定の表、次の契約で使う値、起票者の誤り、逸脱、想定外、送出。**目安は百五十行以内。**
- 証跡の記録 — 命令とその出力、対照の出力、変更範囲の一覧、台帳の応答。

**事実の記録から証跡の記録を行番号で指すこと。**

**Step 6.** PR を作る。**送り出しただけでは統合ではない。**
**分岐が規定の接頭辞で始まっていることを確かめる。**

**Step 7.** 抑止の目印を移動によって解除する。

## 3. 環境が揃っていなかった場合の報告

**Phase A で止まった場合、次を含めて報告すること。**

- 実在したものの一覧
- 欠けていたものの一覧
- 欠けているものそれぞれについて、**何があれば後続が走るか**
- 他のホストから運べるものと、作り直しが要るものの区別
- 作り直しに要する見込み（**実測できない場合は、その旨を書く。推測を数値で書かない**）

**これは失敗の報告ではない。次の契約の設計に直結する情報である。**

## 4. 環境を新たに構築しない

**本契約は、欠けている環境を作る契約ではない。**

導入や構築は環境を変える操作であり、**他の作業へ影響しうる。**
**欠けていると分かったら、止めて報告する。**構築するかどうかは起票者と利用者の判断事項である。

**ただし、読み取りだけで済む確認は行ってよい。**

## 5. 禁止

**以下は実行者の操作に対する禁止であり、自動同期の仕組みによる配布を含まない。**

1. 分割の定義を変えない。
2. 生の記録へ書き込まない。
3. 凍結源を変えない。
4. 測っていない値を書かない。**測れなかったものは、測れなかったと書く。**
5. **投影と集約の再生成を行わない。**
   四台で別の契約が同時に走っており、これらは必ず衝突する。
   **全ての PR が統合された後、一台で一度だけ回す。**
6. **環境を新たに構築しない。**（第 4 節）
7. **雑音除去の実装を書き換えない。**
8. **効果が無いと書かない。**（第 1 節 1.1）
9. **秘匿の値を出力しない。** 判定に要るのは長さと有無だけである。
   **判定するのは件数ではなく形である。**
   変数名・説明文・指紋・公開鍵は、それ自体では危険ではない。

## 6. 想定外への対処

- **道具が無い、権限が無い、対象が零件** — **そのまま採用しない。**
  何を、どの状態で、どの方法で見た結果かを確かめてから記録する。
  **ただし本契約では、確かめた結果として不在が確定したなら、それは正当な成果である。**
- **禁止領域の検査が失敗する** — 本契約は新しい run を作りうる。
  検査は run を作る契約を構造的に通せないことが実測されている。**失敗そのものは契約違反ではない。**
  **内訳を一件ずつ示すこと。**
- **終了コードを件数と呼ばない。** 数えるなら数える命令を使う。
- **配列の添字の書式はシェルによって違う。** 過去に二契約続けて終了コードの検査が空振りしていた。
- **命令ごとに新しいシェルが起きる実装系がある。** 読み込みは同じ命令の中に入れる。
- **履歴を読む操作は頁送りを無効にすること。**
- **背景で走らせた処理の出力を、完了の前に読まないこと。**
- **読み込みの遅い仕組みに注意する。** 配列を保持する形式には、参照のたびに全体を展開し直すものがある。
  ループの中で繰り返し参照すると記憶が尽きる。**ループの前に実体化すること。**

## 7. 完了判定

**判定が通ったことは、その判定が働いていることを意味しない。**
各行に「空振りでないことの確認」を書く。**空欄にしない。「確認した」と書かない。**

| # | 判定 | 期待 | 空振りでないことの確認 |
|---|---|---|---|
| a | 環境の棚卸しを行った | 実在するものと欠けているものが一覧になっている | 存在しない経路を同じ方法で調べれば、不在として返るはずである |
| b | 欠けているものの補い方を記録した | 何があれば走るかが書かれている | 欠けているものが零件なら、この行は適用外と書く |
| c | 雑音除去が信号を変えている | 施す前と後で信号が違う | 違わなければ、雑音除去は働いていない |
| d | 施さない腕では信号が変わらない | 元の信号と一致する | 一致しなければ、意図しない加工が入っている |
| e | 変化の量を集合の差で求めた | 差として得られている | 部分一致で数えた場合と値が異なるかを確かめる |
| f | 所要時間を実測した | 秒または分で記録されている | 零または負なら測り方が誤っている |

| j | 効果量と倒れた個数の双方を出した | 双方が記録されている | 片方しか無ければ満たされない |
| k | 判定を行っていない | 有意・非有意の語が結論に現れない | 現れていれば範囲を越えている |
| l | 効果が無いと書いていない | 見える大きさより小さい、という書き方になっている | 効果が無いと書かれていれば満たされない |

## 8. 起票者からの申し送り

**起票者は実行環境を持たない。** 以下は前提であって実測ではない。**違っていたら報告すること。**

1. **当該ホストに環境が揃っているかは未確認である。** 揃っていない可能性が高いと見ている。
   **揃っていなくても、それを確かめたことが成果である。**
2. **入口として挙げた実装は、名が変わっている可能性がある。** 実装を読んで決めてよい。
3. **雑音除去の実装が本番側の入口から呼べるかは未確認である。**
   代理側にしか無い場合は、**そこで止めて報告すること。**
   **実装を新たに書き起こす契約ではない。**
4. **既存の run に所要時間が残っていない。** 見積もりは実測から立てる。
5. **本契約と同時に、判定則を確定させる別契約が走っている。**
   本契約は判定しない。数字を出すところまでが範囲である。
6. **効果が見えなかった場合が、本契約にとっての成功である。**
   **しかし、見えなかったことを効果が無いと読み替えてはならない。**

## 9. 報告

事実の記録と対の記録を埋めて記録すること。逸脱は必須である。逸脱が無い場合も、無かった旨を一件書く。

**起票者の誤りを見つけたら、遠慮なく記録すること。**
何が誤っていたか、指示どおり実行すると何が起きたかの二つを含めること。
**これは起票者を改善するための記録である。**
