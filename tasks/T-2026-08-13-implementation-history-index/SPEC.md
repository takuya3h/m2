# 実装の完了報告を構造化し、投影として読めるようにする

**task_id:** `T-2026-08-13-implementation-history-index`
**kind:** `impl`
**depends_on:** `T-2026-08-12-contract-distribution-via-notion`
**実行ホスト:** `lecun`

## Goal

実験には一次証跡と索引と投影が揃っているが、**実装には索引も投影も無い。**
完了報告は散文であり、全文を読まなければ何が終わったか分からない。起票者は会話の
記憶に頼っており、セッションをまたぐと失われる。

**構造化した対を一次証跡へ足し、投影を作る。**

`RESULT.md` を解析して要約を作ってはならない。**散文の解釈は捏造を生む。**
実行者が事実だけを構造化して書く。

得られるもの。全文を読まずに把握できること。申し送りが一箇所に集まること。
**起票者の誤りの型と頻度が数えられること。** 依存の連なりが見えること。

併せて、資格情報の読み込みが**平文の設定ファイルを黙って上書きする**問題を直す。
編集してから読み込むと編集が消える。実際にこれで原因の切り分けが長引いた。

### 起票者からの申し送り

起票者の検査コマンドが検証対象を検証できていない誤りが 12 task 連続で発生している。
直近では、配布した本文が外部の記法として解釈されて壊れた。要約値の照合が無ければ
壊れた契約を取り込んでいた。

実行環境の対話シェルは bash ではない。**変数の直後に記号が続く場合は波括弧で囲むこと。**

**本 SPEC の検査も同型の誤りを含みうる。** 次を守ること。

| # | 注意 |
|---|---|
| 1 | 一致件数が 0 のとき、別の探し方でも 0 になることを確かめる |
| 2 | 仕組みの挙動は実装を読んでから信じる |
| 3 | 記録を作る流れに表示用の切り詰めを混ぜない |
| 4 | 検査が対象の実際の位置を測っているかを確かめる |
| 5 | パイプは部分シェルを作る。環境変数の確認では使わない |

# Phase A — 完了報告の様式

## Task 1: 構造化された対を定める

**Files:** Create `tasks/_schema/result.schema.json`、Create `tasks/_templates/result.yaml`

- [ ] **Step 1: 既存の様式を読み、書き方を揃える**

`tasks/_schema/spec.schema.json` と `tasks/_templates/` を読む。独自の方式を持ち込まない。

- [ ] **Step 2: 様式を定める**

項目は次のとおり。

| 項目 | 内容 |
|---|---|
| `result_version` | 1 |
| `task_id` | ディレクトリ名と一致すること |
| `status` | pass / partial / stopped |
| `host` `branch` `pr` `merged` | 実行の場所と起票 |
| `gates` | id と verdict の対。verdict は pass / ask / stop / skip |
| `tests` | before_failed / after_failed / after_passed |
| `deviations` | 件数 |
| `issuer_defects` | type と note の対 |
| `followups` | 申し送りの本文 |
| `unknowns` | 断定できなかった事項 |
| `commits` | 識別子の並び |

`issuer_defects.type` は次の 4 種に固定する。

| 型 | 意味 |
|---|---|
| `check_does_not_check` | 検証コマンドが対象を検証していない |
| `asserted_without_measuring` | 確かめずに断定した |
| `self_contradiction` | 契約の内部で矛盾した |
| `shell_assumption` | 実行環境と異なるシェルを前提にした |

**列挙にない型が要る場合は、完了時に提案として報告する。勝手に増やさない。**

- [ ] **Step 3: 検証を足す**

既存の契約検証へ次を加える。

| # | 要件 |
|---|---|
| 1 | 対があれば様式に沿うことを検査する |
| 2 | **無い場合は失敗としない**。起票直後には存在しない |
| 3 | 識別子がディレクトリ名と一致することを検査する |
| 4 | 誤りの型が列挙のいずれかであることを検査する |
| 5 | status が pass 以外のとき、理由が unknowns か followups にあることを検査する |

**要件 5 が重要である。** 部分的な達成や停止を、理由なく記録させない。

- [ ] **Step 4: 失敗する試験を書く**

`tests/test_result_schema.py` に、**通る例と通らない例の双方**を置く。

正しい記述が通ること。識別子がディレクトリ名と違うと拒むこと。列挙にない型を拒むこと。
停止なのに理由が無いと拒むこと。ファイルが無くても失敗しないこと。版が違うと拒むこと。

- [ ] **Step 5: G1 ゲート — 双方向で確かめる**

試験を走らせ、さらに正しい例と誤った例を一時的に置いて、前者が通り後者が拒まれることを
実地で確認する。**通る例だけを試して満足しない。** 確認後、一時的な例が残っていないことを
`git status --porcelain` で確かめる。

# Phase B — 投影

## Task 2: 投影を作る

**Files:** Create `tools/build_taskindex.py`、Create `tests/test_build_taskindex.py`、Modify `Makefile`

- [ ] **Step 1: 既存の投影の作りを読む**

`tools/build_context.py` の冪等の作り方と、手による編集の検出方法に揃える。
**壁時計を使わない。** 使うと検査が「手による編集」と「時刻の経過」を区別できない。

- [ ] **Step 2: 出力を定める**

| 出力 | 内容 |
|---|---|
| `context/auto/tasks_summary.csv` | 1 契約 1 行 |
| `context/auto/followups.md` | 未処理の申し送りの集約 |

列は次のとおり。task_id、kind、status、host、pr、merged、gates_pass、gates_ask、
gates_stop、tests_before_failed、tests_after_failed、deviations、n_issuer_defects、
n_followups、n_unknowns、depends_on。

kind と depends_on は契約の側から取る。**構造化された対と契約の両方を読む。**

`followups.md` には申し送りの本文と由来する契約の識別子を並べる。
**本文を要約しない。転記する。**

- [ ] **Step 3: 誤りの型を数える**

`followups.md` の末尾に、誤りの型ごとの件数の表を置く。
**これは起票者の改善のための記録である。件数を隠さない。**

- [ ] **Step 4: 失敗する試験を書く**

対が無い契約は行に現れないこと。同じ入力から同じ出力になること。申し送りの本文が
変わらずに転記されること。誤りの型の件数が正しいこと。空でも落ちないこと。
生成物であることが冒頭に書かれること。

- [ ] **Step 5: Makefile へ足す**

`taskindex` と `taskindex-check` を足す。**挿入位置に注意。既存レシピの途中へ入れない。**

- [ ] **Step 6: G2 ゲート — 冪等と検出**

生成を 2 回行い md5 が一致すること。検査が exit 0 であること。
そのうえで `followups.md` へ手で 1 行足し、**検査が非ゼロを返すこと**を確認する。
再生成すると 0 に戻ること。**陽性対照が実際に失敗することを確認する。**

- [ ] **Step 7: 既存の投影が壊れていないことを確認する**

`make context` と `make context-check` を実行する。**新しい出力を既存の検査が
「未知のファイル」として扱わないか**を確かめる。扱う場合は、どちらの検査が何を見るかを
整理して記録する。

- [ ] **Step 8: 本 task 自身の対を書く**

**本 task が最初の利用者である。** 完了時に対を書き、投影に現れることを確認する。

# Phase C — 編集が消える問題

## Task 3: 読み込みが編集を上書きしないようにする

**Files:** Modify `scripts/load_env.sh`

- [ ] **Step 1: 現在の挙動を実測する**

平文の設定を控えたうえで、印となる行を末尾に足す。読み込みを実行し、印が残っているかを
数える。**消えることを実測してから直す。** 消えなければ前提が違うので停止して報告する。
印を足したことが暗号化された設定へ影響していないことも確認する。

- [ ] **Step 2: 直し方を選ぶ**

**復号先を平文の設定ファイル以外にする**のが推奨である。ただし平文を読む他の箇所が
あるかを実装から確かめてから決める。影響があるなら、警告に留める案も検討する。
**選んだ理由を記録する。**

- [ ] **Step 3: 直す**

**変えるのは書き出し先の扱いだけ。** 復号の手順・変数の設定方法・出力の文言には触れない。

- [ ] **Step 4: G3 ゲート — 両方向で確かめる**

修正後に印を足して読み込み、印が残ることを確認する。資格情報が従来どおり読めることも
確認する。そのうえで修正を一時的に戻し、**印が消えることを再確認する。**

**パイプを挟まないこと。** 部分シェルを作ると環境変数の確認が誤る。
**修正前でも印が残るなら、この対照は無効である。** 停止して報告する。

- [ ] **Step 5: 印を消して元に戻す**

印の行を削除し、平文の設定ファイルが版管理へ入っていないことを確認する。

- [ ] **Step 6: 文書化する**

運用手順を述べている箇所へ、**編集と再暗号化の正しい順序**を明記する。
