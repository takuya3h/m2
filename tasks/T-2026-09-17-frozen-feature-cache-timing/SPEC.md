# P→D 側の W1 界面 run で、凍結検出塔の出力をキャッシュしたときの所要時間と結果の同一性を実測する

**task_id:** T-2026-09-17-frozen-feature-cache-timing  **kind:** impl

## 1. 背景

Tier 1 の試算（`docs/stage0/B1_tier1_cost_estimate.md`、T-2026-09-17-tier1-cost-estimate）で、
計画全体の費用のほぼ全部が **P→D 側の検出界面 run（1 本およそ 4 時間、6 epoch × 36〜40 分）** に集中していると分かった。
腕を削る前に、この 4 時間の原因が「凍結した塔に毎 epoch 画像を通し直している」ことかを確かめる。
そうなら、塔の出力を一度保存して界面だけを学習することで、**設計を変えずに** run を縮められる。

利用者の決定（2026-09-17）: 腕は削らない。先にこれを測る。本契約は **GPU を使う**（利用者承認済み）。

原因が実装なら実装を直す。原因が設計なら設計を変える。これは提案関門の失敗時手順の順番であり、
本契約はその識別実験である。

## 3. Task

**コマンドは書かない。実装を読んで決めてよい。** 出力は `audit.md` に残す。

### Task A — 開始状態

1. 作業ツリーの清浄を確かめる。開始前から在る未追跡は移動で退避し、退避先と件数を記録する。`git stash list` の件数も記録する
2. 装置の状態を記録する（`nvidia-smi` の読み取り。他利用者の処理があれば停止して諮る）。**プロセスの計数は `/proc/PID/exe` の解決か
   引数の完全一致で行う。部分一致は使わない**
3. 基準 run を特定する。T-2026-08-29 の run の処方（config、seed、折り、epoch、batch、注入の型）と所要時間と主指標を記録から引く。
   **同じ処方の記録が無ければ、4 時間の基準を新たに回す前に停止して諮る**（escalate_if）
4. 凍結塔の出力の形（層、解像度、次元、フレーム数）を実装から読み、一折り分と 15 動画分の大きさを見積もる。配置先の空き容量と比べる。
   超えるなら停止して諮る
5. `conventions_rev` と `runindex_commit` を実測し spec.yaml の占位を差し替える

### Task B — キャッシュの生成

1. 凍結塔の出力を、界面が要る層について一度だけ保存する。保存の形式と鍵（塔の識別子・凍結源の要約値・解像度・前処理）を決め、記録する
2. **決定性**: 同じ入力で二度生成し、要約値が一致することを確かめる（G2）。塔の識別子（鍵の一部）を変えると要約値が変わることを一度示す
3. 大きさの実測（バイト数。`du -sh` の丸めを実数として扱わない）

### Task C — キャッシュ経路の W1 run

1. 学習経路にキャッシュを読む口を足す。**既存の経路を壊さない**（キャッシュ無しの経路がそのまま動くことを試験で確かめる）
2. 基準と同じ処方・同じ seed・折り A で W1 run を一本回す。壁時計と GPU 時間を記録する。epoch ごとの時間も記録する
3. 主指標を基準と比べる。決定化できるならビット一致を確かめる。できない場合は差を出し、既知の seed 間散らばり（`docs/stage0/` か runindex に
   ある同型 run の σ）と比べる。**散らばりと同程度なら停止して諮る**

### Task D — 比較と W2 への適用可能性

1. 短縮の倍率を epoch 一回あたりと run 全体で別々に出す（キャッシュ生成の時間は別行に置く。run 本数で償却する形も書く）
2. W2（受け取り塔の末端も学習する）について、実装からどの層が学習対象かを読み、キャッシュが効く範囲（末端より手前の出力）を記録する。
   可能なら W2 の run でも一本測る。時間が無ければ UNKNOWN と書き、効く範囲の記述だけ残す
3. 装置の状態を終了後にも記録する

### Task E — 検証と報告

1. L1、L2、`make forbidden-check`、`make spec-check TASK=T-2026-09-17-frozen-feature-cache-timing`、試験（既存の失敗数が増えていないこと）
2. 完了判定 a〜h を実測で埋める
3. `docs/stage0/C1_frozen_feature_cache_timing.md` に、基準とキャッシュ経路の所要時間、主指標の比較、キャッシュの大きさ、W2 の範囲、
   Tier 1 試算の計算器（T-2026-09-17-tier1-cost-estimate が置いた `tools/` の計算器）に入れ直した値を書く
4. `RESULT.md`、`result.yaml`（版 3）、`audit.md`、`tasks/inbox.d/T-2026-09-17-frozen-feature-cache-timing.md`
5. commit、push、**PR の base は `phase0`**（前の 2 契約は `master` へ出てしまった。`gh pr create` の base を明示する）。
   分岐名が `feat/frozen-feature-cache-timing` であることを記録する
6. 報告後に `.sync-pause` を移動で解除する

## 4. 禁止事項

**禁止は実行者の操作に対するものであり、同期処理による配布を含まない。**

1. 凍結源を変えない。塔の重みに勾配を流さない（W1 の定義）
2. 基準 run と処方を揃える。epoch、batch、seed、注入の型、解像度を変えない。**速くするために処方を変えることは本契約の目的に反する**
3. 折り A 以外を使わない。test で選定しない（val で見る）
4. `context/auto/*` と `tasks/inbox.md` を再生成しない
5. `data/raw`、`data/external`、`runindex/**`、`context/conventions.md` に触れない。キャッシュは `data/processed/` 配下か利用者が指定する共有領域に置く
6. 既存の `tasks/*/` を変えない。開始前から在る未追跡を消さない
7. 他利用者の処理を止めない。装置が使われていれば停止して諮る
8. 外部への送信は `make task-report` 以外の経路で行わない

## 6. 想定外と停止条件

- 同じ処方の基準 run が無い → 回す前に諮る（4 時間の追加になる）
- キャッシュが配置先に収まらない → 諮る
- 決定化できず差が散らばりと同程度 → 諮る（キャッシュ経路が結果を変えている可能性）
- 装置が使われている → 諮る
- キャッシュしても短縮が小さい（例: 2 倍未満）→ それ自体が結論。原因が塔の順伝播でないことを意味する。停止せず報告する
