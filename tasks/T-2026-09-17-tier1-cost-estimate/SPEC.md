# Tier 1 の総量（run 本数 × 所要時間）を Stage 0 の実測から試算する

**task_id:** T-2026-09-17-tier1-cost-estimate  **kind:** analysis

## 1. 背景

関門 G0 の三条件目「所要時間から Tier 1 が締切に収まるか判明」が未成立。
利用者はこの試算で投稿先の主目標（IPCAI 2027 か MICCAI 2027 か）を決める（M §1.5、§5.2 の G0 分岐）。

試算は**実測した所要時間**から積む。所要時間の実測が無い run 型は UNKNOWN として列挙し、代理を置くなら
利用者の承認を得る（decisions_required）。**推定値を実測のように書かない。**

**本契約では GPU を使用しない。** 装置の台数を数えるための照会（nvidia-smi 等の読み取り）は可。学習・推論は走らせない。

## 2. 確定した事実（ホストによらない値だけ）

Notion M（マスター v1）の道筋を写す。実行者は Notion を読めない前提で、必要な部分をここに置く。

### 2.1 Stage 1 の成果物（M §5.2）

D\*-COCO、D\*-ImageNet、P\*-21、P\*-15 の各塔を **5 折りで確定**。折り A は 3 seed。
塔の選定はトーナメント（候補間で recipe・seed 数・探索回数を同一）。二段選定可。
**候補の数はまだ決まっていない。** 試算では候補数を変数（K）にし、K = 2、3、4 の表を出す。

### 2.2 Tier と反復（M §5.3、事前登録）

| Tier | 内容 | 反復 |
|---|---|---|
| 1 | 分母と一致確認、参照入力 4 段、方向 4 腕、D→P の W1・L1/L2・P\*-21、P→D の W1・W2・専用探索・L3・両検出塔、対照、折り A の 3 seed | 5 折り × 5 seed |
| 2 | 送り手掃引 4 点、軸 2 選別、D→P の W2・L0、P\*-15 上の S1 | 5 折り × 2 seed |
| 3 | W3、掃引の追加点、S2 の予備、Cholec80 L0 | 折り A × 3 seed |

縮退順（M §5.3）: 掃引 4 点 → 3 点、検出塔候補の二段選定、seed 5 → 3、探索的腕（W3、L3 の D→P 側）→ D→P の W2。
**P→D の W1・W2・専用探索は最後まで削らない。**

対照（M §4.3、Tier 1 に含む）: 空入力界面（分母）、界面なしとの一致確認、乱数入力、同量非関連特徴（L3 で必須）、

## 3. Task

**コマンドは書かない。実装と記録を読んで決めてよい。** 出力は `audit.md` に残す。

### Task A — 入力の収集

1. 作業ツリーの清浄を確かめる。開始前から在る未追跡は移動で退避し、退避先と件数を記録する
2. run 型を列挙する。少なくとも: 検出塔の学習（COCO 初期化、ImageNet 初期化）、工程塔の学習（21 動画、15 動画）、
   W1 の界面 run（工程側、検出側）、W2 の界面 run（検出側）、評価のみの run（参照入力段、対照）、プローブ
3. run 型ごとに所要時間の実測を Stage 0 の記録から引く。**出所（記録のファイルと行、または run 名）を必ず付ける。**
   無いものは UNKNOWN と書き、代理候補があれば候補として別欄に書く（採用しない）
4. 装置を数える。ホストごとの GPU の種類と枚数を読み取りで記録する。他ホストへ接続できなければ、その旨と
   本ホストの値だけを書く。M の記載（2 枚）との一致・不一致を書く
5. 締切の日付を出所つきで記録する（2.4）
6. `conventions_rev` と `runindex_commit` を実測し spec.yaml の占位を差し替える

### Task B — run の列挙

1. Stage 1: 塔 4 種 × 候補数 K × 5 折り × seed（折り A は 3、他は 1。M §5.1「折り A のみ受け取り塔を 3 seed」）。
   K は変数
2. Tier 1: 2.2 の表の各項目を run に分解する。方向 4 腕 × 参照入力 4 段 × 5 折り × 5 seed を基本とし、
   W1／W2、L1／L2／L3、両検出塔、対照の各項目がどう掛かるかを表にする。**M の項目と run の対応表を出し、
   対応の無い項目を零件にする**（G2）
3. Tier 2、Tier 3 も同じ様式で列挙する（試算の主対象は Tier 1 だが、全体像が要る）
4. 分解の判断で二通りに読める項目は、両方の読みを書いて run 数の幅を出す。**一方に決めて隠さない**

### Task C — 計算器と試算

1. 計算器を `tools/` 配下に置く（名前は実行者が決める。既存の命名に合わせる）。入力は run の列挙表と所要時間表と
   装置の台数、出力は Tier ごとの GPU 時間と壁時計時間。並列度は装置の台数と run 型ごとの同時実行数から決める
2. 試算を出す
   - 基本: 縮退なし、K = 2、3、4
   - 縮退: 縮退順を一段ずつ当てた総量（段ごとに一行）
   - 設計変更一回分: Stage 1 の塔一種を作り直して Tier 1 の P→D 側を測り直す費用（提案関門 B.7 の要請）
3. 対照: 所要時間表をすべて二倍にして総量が二倍になること、装置を二倍にして壁時計時間が半分以下になることを示す
4. 締切との比較: 基本と縮退の各段について、装置を占有できる日数の前提を書いた上で、収まる・収まらないを判定する。
   前提は数値で明記する（例: 装置を一日あたり何時間使えるか）。**利用者が前提を変えて再計算できる形にする**
5. 出力: `docs/stage0/B1_tier1_cost_estimate.md`。所要時間表（出所つき）、run 列挙表（M との対応つき）、
   試算表、縮退表、設計変更一回分、締切比較、UNKNOWN の一覧、計算器の使い方（一行）

### Task D — 検証と報告

1. L1、L2、`make forbidden-check`、`make spec-check TASK=T-2026-09-17-tier1-cost-estimate`、計算器の試験
2. 完了判定 a〜h を実測で埋める
3. `RESULT.md`、`result.yaml`（版 3）、`audit.md`、`tasks/inbox.d/T-2026-09-17-tier1-cost-estimate.md`
4. commit、push、PR（Draft でない）。分岐名が `feat/tier1-cost-estimate` であることを記録する
5. 報告後に `.sync-pause` を移動で解除する

## 6. 想定外と停止条件

- 主要 run 型（検出塔学習、工程塔学習、W2 界面 run）の実測が無い → 停止して諮る。UNKNOWN で完了扱いにしない
- M の項目が run に分解できない → 両方の読みを書いて諮る
- 他ホストの GPU を数えられない → 本ホストの値と M の記載で進め、前提として明記する
- 実行基盤が書き込みや `rm` を拒む → 回避せず提示
