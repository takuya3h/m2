# 契約の本文を添付として渡し、外部の記法解釈を受けない経路を作る

**task_id:** `T-2026-08-14-bundle-attachment-transport`
**kind:** `impl`
**depends_on:** `T-2026-08-13-implementation-history-index`
**実行ホスト:** `lecun`

## Goal

配布台帳からの取り込みは完成しているが、**起票者が台帳へ書く経路が壊れる。**

起票者は外部の連携機能で本文を書き込む。その入力は**常に記法として解釈される**ため、
見出しや表や区切りが構造へ変換され、文字列としては残らない。実測では、本文が 20 個の
断片へ分解され、行頭の記号が消費され、復元不可能になった。**要約値の照合が働いて
取り込みは拒まれた。**

**本文を添付として置けば記法の解釈を受けない。** その経路を作る。

## いま分かっていること

| 事項 | 実測 |
|---|---|
| 単一の塊として置いた本文の往復 | **5364 バイトが一文字も変わらない** |
| 記法として貼った本文の往復 | **復元不可能に破壊された** |
| 要約値の照合 | **壊れた本文を拒んだ** |
| 送信時の分割 | 取得時には結合されて返る。境界を覚える必要はない |

**添付が同じ忠実性を持つかは未測定である。** それを最初に確かめる。

## 併せて行うこと

鍵を更新したあと、各ホストに古い平文が残っていると**そのホストだけ古い資格情報で
走り続ける。** 実際にこれで論理名が全台で誤った値になった。運用手順へ明記する。

起票者の検査コマンドが検証対象を検証できていない誤りが 12 task 連続で発生している。

実行環境の対話シェルは bash ではない。**変数の直後に記号が続く場合は波括弧で囲むこと。**

**本 SPEC の検査も同型の誤りを含みうる。** 次を守ること。

# Phase A — 添付の往復

## Task 1: 添付が本文を保つかを実測する

**Files:** なし（台帳へ確認用の行を作り、確認後に印を付ける）

**これが本 task の成否を決める。**

- [ ] **Step 1: 添付の仕組みを実装から確かめる**

既存の連携の実装を読み、**添付をどう取得するか**を把握する。

    grep -n "attachment\|file\|external\|url" src/egosurgery/utils/notion_ops.py | head -20

**推測で API を書かない。** 取得の経路が実装に無い場合は、その旨を記録してから設計する。

- [ ] **Step 2: 確認用の本文を作る**

壊れやすい要素を意図的に含める。行末の空白。連続する空行。引用符とバッククォート。
行頭の記号。長い区切り文字。2000 字を超える連続した塊。日本語と英数字の混在。

要約値とバイト数を控える。**記録を作る流れに表示用の切り詰めを混ぜない。**

- [ ] **Step 3: 起票者が添付として置く**

**この段階は起票者が行う。** 実行者は、置かれた行の識別子を受け取って先へ進む。

台帳の行は `T-2026-08-14-probe-attachment` とし、状態は `superseded` にする。
**本番の契約と混ざらないようにする。**

- [ ] **Step 4: 取得して照合する（G1）**

添付の参照先から本文を取得し、要約値を比較する。

Expected: **一致**

一致しない場合、**何がどう変わったかを記録して停止する。** 差の種類によって対処が変わる。

| 差の種類 | 意味 |
|---|---|
| 行末の空白が消える | 添付でも保たれない。経路として使えない |
| 文字化けがある | 符号化の指定が要る |
| 途中で切れる | 取得の頁送りに対応が要る |
| 取得できない | 参照先の有効期限か権限の問題 |

- [ ] **Step 5: 検査が空振りでないことを確かめる**

**陽性対照を置く。** 同じ長さで一文字だけ変えた本文の要約値が異なることを確認する。

一致してしまうなら照合が無効である。停止して報告する。

- [ ] **Step 6: 参照先の有効期限を確かめる**

添付の参照先は期限つきである場合がある。**取得のたびに参照先を取り直す必要があるか**を
実測する。期限があるなら、その長さを記録する。

# Phase B — 取り込み経路への追加

## Task 2: 添付から取り込めるようにする

**Files:** Modify `tools/fetch_task.py`、Modify `tests/test_fetch_task_notion.py`

- [ ] **Step 1: 既存の経路を読む**

現在の実装は、行の本文から塊を集めて結合している。**その前段に添付の判定を足す。**
**取り込みと検証と巻き戻しは既にある。複製しない。**

- [ ] **Step 2: 優先順を決める**

行に添付と本文の両方がある場合の扱いを定める。

| 案 | 内容 |
|---|---|
| 添付を優先 | 記法の解釈を受けないため確実 |
| 本文を優先 | 既存の行と互換 |
| 両方あれば失敗 | 曖昧さを残さない |

**推奨は添付を優先し、無ければ本文へ落ちる。** ただし実装を読んで判断し、理由を記録する。

- [ ] **Step 3: 失敗する試験を書く**

外部サービスへは接続しない。応答を差し替えて経路だけを検査する。

添付があれば添付から読むこと。添付が無ければ本文から読むこと。要約値が一致しない本文は
受け付けないこと。取得に失敗したら明確な理由で失敗すること。**取得した本文は既存の
取り込み経路へ渡されること。**

- [ ] **Step 4: 実装する**

要件は次のとおり。

| # | 要件 |
|---|---|
| 1 | 行に添付があれば、その参照先から本文を取得する |
| 2 | 無ければ従来どおり本文から集める |
| 3 | 取得した本文の要約値を列の値と照合する |
| 4 | 一致しなければ受け付けずに失敗する |
| 5 | 一致すれば既存の取り込み経路へ渡す |
| 6 | 資格情報を出力しない |
| 7 | 参照先が期限切れなら、取り直してから再試行する |

**要件 5 を守ること。** 巻き戻しを複製しない。

- [ ] **Step 5: G2 ゲート — 実地で確認する**

**陽性対照を含める。**

正常系として、Phase A で置いた確認用の行から取り込めること。
存在しない識別子が非ゼロで終わること。資格情報が無いとき非ゼロで終わること。
要約値が合わないとき非ゼロで終わること。

いずれの失敗でも**契約の件数が変わらず、作業領域が清潔である**ことを確認する。

**一つでも成功する、または痕跡が残る場合は停止して報告する。**
