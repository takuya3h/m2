# T-2026-08-30-hts-candidate-acceptance — HTS 候補の受け入れ検証

**task_id:** T-2026-08-30-hts-candidate-acceptance  **kind:** analysis
**本契約では GPU を使用しない。** 実行ホストは andrew。**読み取りのみ。data 配下には書かない。**

## 0. 位置づけ

方針 v2 §19.3 は HTS 完全版（真マスク、把持関係の五クラス定義、手注釈の四動画復活）の組立を
保留にし、§17-14 は「手信号の腕を Stage 2 に入れるなら G1 までに判断が要る」と定めている。
2026-07 の受け入れ検査（scripts/audit_l0_hts_acceptance.py）は現行の派生物を NOT ACCEPTED と
判定したが、そのとき評価したのは一系統だけである。data/annotations 配下には手・把持・マスク系の
候補が複数あり、それらを **組み合わせれば** 基準を満たせるかは測られていない。

本契約は候補を漏れなく棚卸しし、受け入れ基準に候補ごとに当て、
「組める／一部欠落（何が）／組めない」を三値で確定する。**組立は行わない。**
本契約の数値は判定に変換しない。研究判断（組み立てるか）はユーザーが行う。

## 1. 対象の定義（名前で指定しない）

走査の対象は data/annotations の配下すべて。次を含めること。

- 点で始まるファイルとディレクトリ
- 退避先（名前に deprecated 等を含むもの）
- symlink（リンク先も記録する。リンク先が配下外なら「参照先」として別枠に記録し、読み取りだけ行う）
- 既存の受け入れ検査器・README・DEPRECATED 文書が参照する配下外の経路（例として、再構成系の置き場が README に記されている）。**配下外は「参照先」として棚卸しに含めるが、走査の起点は data/annotations に限る**

候補とみなす条件は「手、把持、術具と手の関係、マスク（多角形か RLE）のいずれかの注釈を含む
ファイル」。形式は COCO 形式の JSON を基本とするが、形式で除外しない。読めない形式は
「読めない」と記録する。

## 2. 受け入れ基準

基準は **既存の検査器 scripts/audit_l0_hts_acceptance.py が実装している C1 から C5 の定義を正**とする。
実行者は検査器の実装と、その出力（experiments/audit/l0_hts_acceptance/ の報告）を読み、
各基準が何を数え、何と比べているかを SPEC ではなく実装から確定する。起票者が記憶している
要点は次のとおりだが、**食い違えば実装を優先し、食い違いを報告する**。

- C1 マスクが真のマスクであること（四頂点の矩形は bbox 由来のダミー）
- C2 把持関係の五クラス定義が揃っていること
- C3 手の注釈の総件数が完全版の件数（五万七千百七十三件と記録されている）に達し、欠落していた四動画の分が含まれること
- C4、C5 は実装を読んで確定する

## 3. 手順

### Task 1 棚卸し（Phase A）

- Step 1-1 conventions_rev と created_from を実測し、違えば置換して記録
- Step 1-2 §1 の対象を走査し、候補ごとに次を記録する: 経路、実体か symlink か、形式、画像数、注釈数、カテゴリの一覧、マスクの型（多角形の頂点数分布か RLE か無し）、動画の被覆（どの動画のフレームを含むか）、来歴（生成スクリプトや文書に由来の記載があれば）
- Step 1-3 走査の網羅性を **異質な二方法** で確かめる（ファイル一覧の道具と、版管理の追跡一覧のような同質の二方法ではなく、例えば全ファイル走査と、文書・スクリプトから参照される経路の逆引きの照合）。一致しない差を記録する
- Step 1-4 G1

### Task 2 基準への当てはめ（Phase B）

- Step 2-1 候補ごとに C1 から C5 を当て、基準×候補の行列を作る。数えた値と閾値を併記する
- Step 2-2 **対照**: 既存の検査器を現行の派生物（前回 NOT ACCEPTED とされたもの）に再実行し、同じ判定が再現することを確かめる（陽性: C1 から C3 が落ちる）。マスク型の判定器には、真の多角形を持つ注釈が一件以上あれば「真」と判定され、四頂点だけの注釈は「ダミー」と判定されることを、実データから抜いた例で確かめる
- Step 2-3 手の件数の数え方が既存の記録（四万六千三百二十件）を再現することを確かめてから、候補の合算で完全版の件数に届くかを数える。**重複（同一フレーム・同一 box）は集合で除く**。単純加算しない
- Step 2-4 組み合わせの評価: 基準ごとに「満たす候補があるか」を判定し、全基準を同時に満たす組み合わせが存在するかを確定する。存在しなければ、欠けている基準と、欠けを埋めるのに必要な原資料（例: 生の手注釈や把持注釈）の所在の有無を記録する

### Task 3 結論と送出（Phase C）

- Step 3-1 三値の結論を書く: 組める（組み合わせを明示）／一部欠落（何がどれだけ）／組めない（理由）
- Step 3-2 REPORT.md、candidates.csv、criteria_matrix.csv を destination に置く
- Step 3-3 commit、push、PR。台帳へ報告

## 4. 禁止事項

1. GPU の使用
2. data 配下への書き込み・移動・削除（退避先から戻す操作を含む）。experiments と runindex への書き込みも本契約の destination 以外は禁止
3. context/auto と tasks/inbox.md の再生成（並行契約あり。統合後に一台で回す）
4. 数値の推定を実測として書くこと。測れないものは UNKNOWN
5. 過去の報告・完了済み契約・履歴の書き換え（追記のみ可）
6. 秘匿情報の出力・複製・移動
7. 外部からの取得・外部サービスへの書き込み
8. 候補を「組み立てる」こと（統合ファイルの生成）。評価のための一時的な集合演算は作業領域で行い、終了時に消す

**禁止は実行者の操作に対するものであり、同期処理による配布や衝突ファイルの生成を含まない。**

## 5. 完了判定

| # | 判定 | 期待 | 空振りでないことの確認 |
|---|---|---|---|
| a | 走査の網羅性 | 異質な二方法の一覧が一致するか、差が説明されている | 一方の一覧から一件除くと差として検出される |
| b | 候補の棚卸し | candidates.csv に全候補が §3 Task 1 の欄つきで載る | 点で始まるものと退避先が一覧に含まれる（含まれないなら走査条件を疑う） |
| c | 検査器の再現 | 現行派生物に対する再実行が前回と同じ判定 | 陽性: C1 から C3 が落ちる。落ちなければ検査器か入力が変わっている |
| d | マスク型の判定 | 真の多角形と四頂点ダミーが区別される | 実データから抜いた双方の例で判定が分かれる |
| e | 手の件数 | 既存記録の再現と、候補合算の集合件数 | 重複を含めた単純加算と集合件数が異なる（同じなら重複除去が働いていない） |
| f | 三値の結論 | REPORT.md に一つの結論と根拠の行列 | criteria_matrix.csv の各セルに数えた値と閾値がある（空欄零） |
| g | 変更範囲 | data 配下の変更零。変更は destination と契約ディレクトリのみ | 同じ絞り込みを destination に当てると変更が出る |

## 6. 想定外の扱い

| 事象 | 対処 |
|---|---|
| 検査器の基準と文書の記述が食い違う | escalate。実装の定義で続行し、食い違いを報告に残す |
| 候補が読めない形式 | 読めない旨と形式を記録し、基準は UNKNOWN |
| 参照先が配下外で到達できない | 所在と到達不能の理由を記録し、基準は UNKNOWN |
| andrew の repo の位置・分岐が記録と違う | 実測を優先し、報告する |

失敗時の巻き戻し: 変更は分岐上のみ。停止する場合も分岐と audit を残したまま stopped で報告する。

## 7. 報告の構成

RESULT.md は起票者が判断に使う事実だけを書く。目安は百五十行以内。

- 判定: verdict と関門の結果
- 完了判定: §5 の表に実測値を埋めたもの
- **三値の結論**と、組めない場合に欠けているもの・原資料の所在
- 実測: 次の契約で使う値（候補の経路と件数、組立に要する操作の種類）
- 起票者の誤り: 型と内容。一件三行以内
- 逸脱・想定外・UNKNOWN・判断待ち
- 送出: PR 番号と終了コードのみ

命令とその出力の全文・走査の一覧・対照の出力は audit.md へ置き、RESULT.md からは行番号で指す。
