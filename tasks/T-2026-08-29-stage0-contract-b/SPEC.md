# T-2026-08-29-stage0-contract-b — Stage 0 契約 B（両方向の参照入力四段ほか）

kind: exp。実行ホストは **lecun**（repo は /home/ubuntu/slocal/m2、A6000 二枚）。
**GPU を使用する。** 学習を伴うため、**prereg.md を学習開始前に commit する**こと（G1 の条件）。

## 0. 目的（方針の新版 §19.2 の四項目）

| # | 項目 | 目的 |
|---|---|---|
| B1 | Run 型ごとの一本あたり所要時間 | Tier と縮退の現実性。**投稿先（IPCAI／MICCAI）の判断材料** |
| B2 | 送り手の訓練動画上 mAP と val 動画上 mAP の差 | 積み重ね漏れの大きさ |
| B3 | **両方向**の参照入力四段を既存の塔で暫定測定 | 関門 G0 の材料。**下界であり主証拠にしない** |
| B4 | 強い工程塔（ImageNet-R50 微調整＋TeCNO、十五動画）に対する D→P 四段 | 関門 G1.5 の暫定材料 |

本契約の数値は**判定に使わない**（prereg 参照）。測定の成立が成果である。

## 1. 定義の転記（方針の新版は repo 未配置のため、必要な定義をここに正確に写す）

### 参照入力段（四段。旧 oracle 梯子の置き換え。§9.2）

| 段 | D→P | P→D | 解釈 |
|---|---|---|---|
| 空 | 空入力界面 | 空入力界面 | **分母** |
| 予測 | 塔の予測 | 塔の予測 | 実現値 |
| 正解 | 正解の術具在否（既存 B2a 系なら正解 presence） | 現フレームの正解工程（one-hot と持続時間） | 誤りを除いた参照 |
| 正解 ⊕ 予測 | 正解と予測の連続スコアの結合 | 正解と予測の事後の結合 | 予測の上位集合。**上限として使うのはこの段のみ** |

解釈規則（事前登録済み）: 「予測が正解を上回る」は天井の証拠ではなく**離散化による情報損失の証拠**。

### 学習範囲 W1（§5.3。本契約は W1 のみ使う）

界面と、受け取り塔の**入力適合層のみ**を学習する（入力次元の変化を吸収する層。それ以外は凍結）。
D→P: 送り手 D は完全凍結、P の backbone と時系列核の本体は凍結。
P→D: 送り手 P は完全凍結、D の backbone・エンコーダ・デコーダ前段は凍結。
**分母（空段）の腕にも同一の界面を空入力で持たせ、同一水準・同一スケジュールで学習する**（容量対照）。

## 2. 変更対象

- experiments/transfer/ 配下の新規 run（本契約の出力。命名は conventions#naming に従う）
- 最終 Phase での **make runindex による自 run の収穫**（exp の完了条件。手編集は禁止）と投影の再生成

- 契約ディレクトリと受け皿

data 配下の生データ・分割・既存キャッシュへは書き込まない。既存 run は変更しない。

## 3. Phase A — 前提の実測と prereg の commit（G1）

### Step A-1 参照の解決と凍結源欄の追加

**分母は起票者が投影から解決済みで、実値が spec.yaml に入っている。**
現物の索引に同じ experiment_id が在ること、三 seed・val・ばらつき有りを満たすことを確かめる。
満たさなければ停止（stop_conditions）。

**凍結源の欄は起票者が外してある。** 起票者は索引の run 名を読めず、
推測で書けば形式検査か実在検査のどちらかで落ちるためである。実行者が次を行う。

- 索引で **Relation-DETR S0-frozen（seed42）に対応する検出 run** を特定する。
  手掛かりは `frozen_source_tag` が `relation_detr_seed42` であること、
  凍結 ckpt が `third_party/Relation-DETR/checkpoints/incoming/seed42/best_ap.pth` であること
- `inputs.frozen_source` を `{ref: "run:GROUP/RUN_NAME", verify: ckpt_sha256}` の形で**追加**し、
  ckpt の sha256 を検証する。これは本契約の手順であり逸脱ではない
- **一意に定まらない場合は候補を列挙して停止**（escalate）。適当に選ばない

追加・確認の後に L1・L2 を通す。

### Step A-2 実装可否の実測

四段それぞれについて、既存実装で作れるかを確かめ、{可能／要最小追加／不能} を確定する。

- D→P 既存塔: B2a 系（presence 入力の TeCNO）は正解 presence 入力の前例が索引にある
  （b2a_det2phase_oracletool）。四段の入力を作る経路を特定する
- P→D 既存塔: 検出器へ工程情報を入れる経路が無い場合、**入力適合層と界面の追加（W1 の範囲）に限り
  新設してよい**。それを超える改変が要るなら escalate
- B4 の工程塔: ImageNet-R50 の微調整と TeCNO の学習経路を特定する
- **各 run 型の所要時間を、最小の試走（一 run 以下）で見積もり、B1 の初期値とする**

### Step A-3 prereg の commit

prereg.md を確定し、**いかなる学習 run の開始よりも前に commit** する。
commit hash と時刻を spec.yaml の prereg 欄へ記入する。時系列は判定 b で検証する。

## 4. Phase B — D→P 四段（既存工程塔）と B2

- **D→P 四段 × 三 seed = 十二 run**。既存の工程塔（TeCNO、キャッシュ特徴上）で、
  §1 の四段の入力を与えて学習・評価する。空段は容量対照（空入力の同一界面）とする
- 分割: 学習は train、測定は val。**test には触れない**
- **B2**: Step A-1 で確定した凍結源の検出器を訓練動画と val 動画で評価し、mAP の差を測る
  （評価のみ。学習しない）
- 各 run の実時間（学習・評価別）を記録する（B1）

## 5. Phase C — P→D 四段（既存検出塔・W1・一 seed）

- **P→D 四段 × 一 seed = 四 run**。検出器は Step A-1 の凍結源を凍結し、
  W1（入力適合層と界面のみ学習）で §1 の四段を与える。空段は容量対照
- 工程の「予測」段には、既存の工程塔の予測（再評価済みの relationdetr 側 checkpoint の出力等、
  実在するもの）を使う。どれを使ったかを notes に記す
- 主指標は mAP。各 run の実時間を記録する（B1）

## 6. Phase D — 強い工程塔と D→P 四段（B4）

- **塔の構築（一 seed）**: ImageNet-R50 を十五動画の工程ラベルで微調整し、その特徴で TeCNO を学習する。
  これが「強い工程塔」の暫定版である
- **D→P 四段 × 三 seed = 十二 run**: 強い工程塔を受け取り手に、W1 で §1 の四段を測る
- 塔単体の val 性能も記録する（G1.5 の文脈で使う）

run 総数の見込み: 12 + 4 + 塔 1 + 12 = **二十九**。縮退（seed 削減・段の削減）が必要になったら
G2 の ask で判断を仰ぎ、縮退の内容を報告に明記する。

## 7. Phase E — 収穫・検査・送出

### 完了判定

**四列目は実測で埋める。「確認した」とだけ書くことは認めない。**

| # | 判定 | 期待 | 空振りでないことの確認 |
|---|---|---|---|
| a | 四段の成立 | 両方向とも四段の主指標の表が揃う（不能の段は理由つきで明示） | 空段と他段の値が全て同一でないこと（測定が入力に感応している）。同一なら測定不良として報告 |
| b | prereg の時系列 | prereg の commit が全学習 run の開始より前 | prereg の commit 時刻と各 run の開始時刻の対照表 |
| c | B1 | run 型ごとの所要時間の表（学習・評価別、n は一以上） | 表の各行に実測の対象 run 名が付いている |
| d | B2 | 訓練動画と val 動画の mAP と差 | 同一 ckpt・同一 recipe であることを config で示す |
| e | 索引 | 全 run が task_id 付きで索引に現れる。収穫の差分が「追加のみ」（run 単位の表）で、追加集合は本契約の run と一致 | 集合差の全量。集約表の変更は判定列の不変で確認（先契約の提案規約を先行適用し、その旨を明記） |
| f | 変更範囲と不変 | 変更が §2 に限られ、既存 run・data・分割が不変 | 差分全量で対象外零件。凍結源 ckpt の sha256 が作業前後で一致 |

forbidden-check は収穫により runindex/ で非零になる既知の制約がある。
違反の全件が本契約の許可分（収穫の出力）と集合一致することを示すこと（先契約の前例に従う）。

### 送出

- 受け皿へ記録し、投影を再生成してから commit する
- 分岐が feat/ で始まることを確かめる。**PR が存在する状態で終える。** base は分岐の起点と同じ分岐
- 台帳へ完了報告を返し、run 台帳（notion_run_ledger）へも結果を記す

## 8. 禁止事項

1. 分割の再定義。test への接触
2. 凍結源の変更・再学習（no_frozen_change。W1 の凍結表に従う）
3. runindex の手編集（収穫は make runindex のみ）
4. data 配下の生データ・既存キャッシュへの書き込み
5. 評価規則の新設・変更（既存の評価実装を使う）
6. prereg の commit 後の書き換え（変更は meta.amendments へ追記）
7. 数値の推定を実測として書くこと。測れないものは UNKNOWN
8. 本契約の数値による仮説の採否判定
9. 秘匿情報の出力・複製・移動

**禁止は実行者の操作に対するものであり、同期処理による配布や衝突ファイルの生成を含まない。**

## 9. 想定外の扱い

| 事象 | 対処 |
|---|---|
| 所要時間が見積もりを大きく超える | G2 で ask。縮退案（seed 削減→段の削減の順）を添えて判断を仰ぐ |
| P→D の入力経路が W1 の範囲で作れない | escalate。P→D 四段を「不能（理由）」として他を続ける判断も添える |
| 予測段に使える工程予測が実在しない | 使える実在物を列挙して ask |
| 学習が発散する・NaN | 当該 run を失敗として記録し、seed か初期化を変えず**同条件で一度だけ再試行**。それでも失敗なら不能として報告 |
| GPU の同時利用者が現れる | 一枚に縮めて続行し、その旨を B1 の表に注記 |
| 収穫で既存 run の行が変わる | run 単位の表で変更が出たら停止。集約表は判定列不変を確認 |

失敗時の巻き戻し: 変更は分岐上のみ。run ディレクトリは分岐外の生成物だが、
失敗 run も削除せず失敗として記録する（記録の保全）。停止時も audit を残して stopped で報告。

## 10. 報告の構成

RESULT.md は起票者が判断に使う事実だけを書く。目安は百五十行以内。

- 判定: verdict と関門の結果
- 完了判定: §7 の表に実測値を埋めたもの
- **四段の表**（両方向。値と段差のみ。解釈は書かない）
- **B1 の表**（run 型 × 所要時間。投稿先判断の材料）
- B2 の差、B4 の塔単体性能
- 実測: 次の契約で使う値（収穫後の索引件数・runindex_commit・GPU 利用実績）
- 起票者の誤り／逸脱・想定外・UNKNOWN／送出（PR 番号と終了コード）

命令とその出力の全文・run 一覧・時系列の証跡は audit.md へ置き、行番号で指す。
