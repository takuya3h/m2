## 1. 研究の全体像（現在の到達点）

### 1.1 何を扱う研究か

開放手術（open surgery）を**一人称視点（egocentric）**で撮影した映像から、複数タスクを統合的に認識する。対象タスクは①術具検出、②手検出、③工程認識（phase）、④手–術具関係の4つ。多くの既存手術ビデオ研究は腹腔鏡（laparoscopic, Cholec80 等）であり、視野が定まらず手・術具のオクルージョンが多い**開放手術 × 一人称視点が未踏ドメイン**である点が出発点。

### 1.2 主張の核（ピボット後）

「術具検出はこのモデル、工程認識はこのモデル、組み合わせるとこれがベスト」という**“最良の組み合わせ発見”論文を脱却**し、**タスク結合の原理そのもの**を主張する（指導教員コメントへの応答）。結合の価値は性能だけでなく、最終的には **negative transfer の回避**・**ラベル効率**といった原理的な軸で示す。

### 1.3 データの最重要注意点

- **EgoSurgery-Phase と EgoSurgery-Tool はデータが別物**。Phase は21動画全体、Tool はその部分集合15動画に bbox を付けた拡張。
- **split が一致しない**：Tool の **10/2/3 動画 split** ≠ Phase 論文の **14/2/5 動画 split**。結合手法は bbox と phase の両ラベルが必要なため、**Tool subset 15動画・10/2/3 split に統一**する（§2.5(b) §3.4）。論文ベンチ（14/2/5）と本研究の数値は**直接比較不可**で、並べる場合は別系統の再実験が必要。

## 2. これまでに変更した方針（時系列＋構造）

> 上ほど新しい。★は今回（2026-06-14）の決定。

### 2.1 ★研究順序の転換：仮説ファースト → 分析ファースト（2026-06-14, §2.5(b) §7）

**変更前（§13 の想定）**: ドメイン構造を眺める → 新結合 H-C を発想 → 既存結合と比較して優位を示す（＝仮説ファースト）。
**変更後**: 既存結合を複数実装 → 単一タスクとの Δ を実測 → 差の要因を分析 → **観察に基づいて**仮説を立てる（＝分析ファースト）。

**変更の理由（なぜ分析ファーストが研究として強いか）**:

1. **仮説の出所が変わる** — 「ドメイン構造から発想した」より「既存結合のこの失敗を観察した→だからこう繋ぐ」の方が motivation として圧倒的に強く、提案が後付けでなく必然になる。
2. **negative transfer を実測してから語れる** — 異粒度（検出×工程）は素朴結合だと悪化しうる。実測して初めて、H-C のような「いつ繋ぐかを動的制御する」必要性が示せる。
3. **最悪でも論文が立つ** — 既存結合の open surgery × 異粒度への適用と分析それ自体が未報告の貢献になりうる（§2.6 二段構えと整合）。

**§13 仮説の扱い**: H-C / H-H / H-A は破棄せず、「STEP C の観察で選ぶ/作り直す**仮説プール**」に格下げ。これにより「既存結合を試さずに新結合を発想している」という引っ掛かりを解消する。
**記録**: 意思決定ログ「研究順序を分析ファーストへ変更」（Impact: high / active / scope）。

### 2.2 比較の土台：検出側三角形と S0-frozen 新設（2026-06-02, §2.5(b) §4）

backbone を凍結する方針を採ったため、**既存 S0（backbone を fine-tune して mAP 計測済）はそのままでは Δ_detection の分母になれない**（凍結 / fine-tune の効果が交絡）。解消策として **S0-frozen**（凍結 backbone ＋ 検出ヘッド）を新設：

- Step1: 既存 S0（fine-tune）で ResNet-50 を検出に適応 → その重みを**凍結源**として固定。
- Step2a: 凍結 backbone ＋ 検出ヘッド = **S0-frozen**（Δ_detection 分母）。
- Step2b: 凍結 backbone ＋ 時系列ヘッド = **S4**（Δ_phase 分母）。
- Step2c: 凍結 backbone ＋ 検出 ＋ 工程 ＋ 結合機構 = **S6**（結合手法）。
- → Step2a/2b/2c が同一凍結 backbone を共有し、両 Δ が清浄になる。

### 2.3 工程認識ベースライン S4 の設計確定（2026-06-02, §2.5(b) §1–3）

EgoSurgery-Phase 論文（Fujii et al., MICCAI 2024）を精査し、工程認識モデル12候補を整理。**結合手法と公正比較するための S4 設計を確定**（詳細は §4.2 の表）。核心原則：**S4 は「最強の単独工程モデル」ではなく「結合手法から検出を引いたもの」**。S4 を独立に最適化してはいけない。

### 2.4 重大論点の発見：eval recipe の2系統分裂（2026-06-02, 失敗知見 P1・open）

検出 Run が2つの test_cfg で混在していることを発見（詳細は §4.3）。Δ の土台が揺れており、`DeltaCalculator` が `InconsistentRecipeError` を出す状態。**STEP A 着手前に解消すべき最優先ブロッカー**。

### 2.5 大方針の転換：マルチタスク相互改善 → タスク結合の原理提案（2026-05-28, §13）

指導教員の4コメント（テーマが広すぎ／組み合わせ発見からの脱却／ベースラインを絞りすぎない／ドメイン独自の工夫）を受け、研究フレームを再構成。タスク結合サーベイ（4層分類）を実施し、新結合の仮説プール H-A〜H-I を導出、上位3＝H-C / H-H / H-A を特定。
**注**: Notion 本体（§0〜§16）は旧フレーム H1–H4「相互改善」の記述が残存。再フレーミングは §13 と §2.5(b)・本書に集約されており、本体への全面反映はマイルストーン単位で後追いする。

## 3. タスク結合サーベイの要点（仮説プールの背景）

既存のタスク結合は **4層** に整理できる（このマップが全体の背骨）：

| 層 | 結合が起きる場所 | 代表手法 |
|---|---|---|
| **L1 パラメータ共有** | エンコーダの重み | hard/soft sharing |
| **L2 特徴相互作用** | 中間特徴マップ | Cross-stitch, MTAN |
| **L3 予測相互作用** | タスクの「予測」 | PAD-Net, MTI-Net, Cross-Task Consistency |
| **L4 最適化** | 損失・勾配 | Uncertainty Weighting, PCGrad, CAGrad, FAMO |

仮説プール（§13 由来・格下げ済）と4層上の位置：

- **H-C（不確実性駆動の双方向結合）** = L3＋L4 の融合。**最大の新規性**（予測レベルの双方向不確実性伝播は世界的にほぼ未開拓）。Kendall&Gal の単方向・損失レベル重み付けを超える主張。
- **H-A（トリプレット畳み込み）** = L3 の極限（複数タスクを単一トリプレット構造に畳み込む）。統一の土台だが単独では新規性が弱く、open surgery×ego×4タスクの再定式化で成立。
- **H-H（ラベル効率結合）** = 結合を半教師信号に転用する応用。主張軸は既出だが本タスク構成での実証は空白。

**最大の白地** = 検出（疎 instance）×工程（時間区間）×関係（graph）という**異粒度タスクの構造的結合**。既存 MTL の大半は同一画素粒度の密予測（depth/seg/normal）であり、ここが未踏。

## 5. 今後の進め方（STEP 0 → A → B → C → D）

### 5.1 全体フロー

```
STEP 0  土台を固める（最優先ブロッカー）
        ├─ eval recipe を公式に一本化
        └─ 凍結源 backbone を確定（暫定 Relation-DETR）
            │
STEP A  単一タスク基準点を確定
        ├─ S0-frozen（凍結backbone + 検出ヘッド）… Δ_detection の分母
        └─ S4（凍結backbone + 時系列ヘッド）    … Δ_phase の分母
            │
STEP B  既存結合を「複数」実装し Δ を測る  ← 研究の本体（いま着手）
        素朴MTL → 片方向 → 予測蒸留 → ドメインSOTA …（比較群 6手法）
            │
STEP C  Δ が出た/出ない理由を分析
        per-class / 境界 / negative transfer / タスク自信の相補性
            │
STEP D  観察から仮説を立てる
        §13 候補（H-C等）を「この観察への解」として選ぶ/作り直す
            │
        └─（ループ）STEP D の仮説を STEP B の比較群に新手法として戻し、同一土台で検証
```

### 5.2 STEP 0：前提ブロッカーの解消（着手の前提）

1. **eval recipe を公式に一本化** — どちらを公式にするか決定 → `build_eval_recipe()` に一本化 → S0-frozen / S4 / 結合を同一 recipe で計測 → `DeltaCalculator` の `InconsistentRecipeError` 保護を検出・工程**両方**に適用。
   - **決定的な一手**: まず **1モデルを両 recipe で再 eval**（再学習なし）して **Δ_recipe の実測値**を出す。差が無視できる（〜0.2–0.3pt 未満）なら作業最小の **score_thr=0.0系を公式化**（2モデルのみ再 eval、凍結源そのまま）。差が有意なら意図的に決定し全 Run を再 eval。
2. **凍結源 backbone を確定** — 暫定 Relation-DETR。これで S0-frozen / S4 / 結合が同一 backbone を共有。

### 5.3 STEP A：単一タスク基準点（ほぼ設計済）

- **S0-frozen**: 既存 S0（fine-tune）で ResNet-50 を検出適応 → 凍結 → 検出ヘッドを載せて mAP 計測。Δ_detection の分母。
- **S4**: 同じ凍結 backbone に時系列ヘッド（まず TeCNO）。Δ_phase の分母。
- 2段方式のため、凍結源が後で変わっても **Stage1 特徴の再抽出のみ**で低コストに再走可能。

### 5.4 STEP B：既存結合を複数試す（研究の本体）

サーベイ4層から、検出×工程（異粒度）に適用可能なものを選定。**実装順は下表の優先度順（素朴 → 構造的）**。

| 層 | 手法 | 役割 | 優先度 |
|---|---|---|---|
| L4 最適化 | 共有エンコーダ + タスク別ヘッド MTL（+ Kendall&Gal 不確実性重み） | 結合「なし/重み調整のみ」の下限。素の MTL が Δ を出すか | **必須・最初** |
| 片方向 | 検出 → 工程 pipeline | 単方向の結合。後で双方向性の価値を測る基準 | **必須** |
| L3 予測相互作用 | PAD-Net / MTI-Net 型 予測蒸留 | あるタスクの予測を他方へ蒸留。構造的結合の代表 | 主要 |
| ドメインSOTA | MT4MTL-KD / SSG-Com | 外科の既存結合。ドメイン内比較として必須 | 主要 |
| L3 整合 | Cross-Task Consistency | 整合制約。教師なし不確実性（H-C の踏み台）と接続 | 余力 |
| L2 特徴相互作用 | Cross-stitch / MTAN | 特徴共有型。異粒度で素朴に効かない→「なぜ」が論点 | 参考 |

**勾配系（PCGrad / CAGrad / FAMO）は結合の比較群ではなく併用アドオン。主軸に置かない。**

### 5.5 STEP C：差の要因分析（＝次の仮説の種）

- per-class / per-phase で「どこが改善・悪化したか」の所在を特定。
- 形状類似ペア（Forceps↔Tweezers。§16.7 で Forceps AP 0.238 が Tweezers/Needle Holders に取られる混同を実証済）が結合で救えたか。
- 工程境界フレームで検出が安定したか（H1 の核）。
- negative transfer はどの結合で・どのクラスで出たか。
- 「タスクの自信が相補的か」を実データで確認（H-C の前提検証）。

### 5.6 STEP D：観察から仮説を立てる

STEP C の観察を踏まえ、§13 の仮説プール（H-C / H-A / H-H）から「この観察への解」として最も筋の良い結合原理を**選ぶ / 作り直す**。立てた仮説は STEP B の比較群に戻し、同一土台で検証する（探索と検証が地続き）。

## 6. 公正比較の鉄則（全 STEP 共通の制約）— 「比較の三角形」

主張は2本の Δ で構成：**Δ_detection =（結合 − S0-frozen）** と **Δ_phase =（結合 − S4）**。これが有効であるための条件：

- **同一土台 = {凍結backbone・初期化・解像度・検出ヘッド・各損失・スケジュール・データ/split・fps・eval recipe・seed}** を全条件で共有し、変えるのは「タスク/結合の有無だけ」。
- **各ステップで1軸だけ変える**（§13 原則）を厳守。
- **交絡の禁止**：正則化の非対称（結合だけに入れない）、計算予算の非対称（結合に多 epoch を与えない）、指標・推論 protocol の混在（online/offline、relaxed/strict Jaccard を混ぜない）、backbone 初期化のすり替え。

## 8. 考慮すべき前提・リスク（見落としやすい点）

1. **主貢献の性格が変わりうる** — 分析ファーストを徹底すると、主貢献が「新結合手法の提案」でなく「**既存結合の異粒度・open surgery 挙動の体系的分析 ＋ そこから導いた結合**」になりうる。CVPR では「分析＋手法」型として強い一方、**指導コメント②（組み合わせ発見を脱却し新しい仮説を立てる）との接続を、STEP D で必ず新規な結合原理に到達する設計にして担保する**必要がある。
2. **DETR は基本 NMS-free** — set prediction のため `nms_iou`/`nms_pre` は多くの DETR で no-op の可能性。だとすると eval recipe 2系統の差は実質「score_thr（ほぼ同一）＋ max_per_img」だけに縮み、**問題が見かけより小さい可能性**。Co-DETR だけは補助 one-to-many ヘッドで NMS が効きうる。
3. **COCO 標準は max_dets=100** — locked-down(300)も score_thr=0.0系(None)も**どちらも COCO 標準と不一致**。外部の COCO 系数値と並べる予定があるなら latent な問題（術具は疎なので実害は小さい見込みだが要 sanity check）。
4. **recipe 決定は S4 の特徴抽出をブロックしない** — recipe が効くのは Δ_detection の比較可能性。**凍結 backbone の特徴はヘッドの後処理に依存しない**ため、凍結源さえ暫定確定すれば S4 の特徴抽出は先行できる。
5. **“eval recipe 一本化” は実は2つのロック** — 検出 recipe（本件）＋ **工程 recipe**（online flag・Jaccard relaxed/strict 等）。検出側を決めても工程側のロックは別途必要。
6. **データ整合性（再掲）** — Phase 論文 split（14/2/5）と本研究 split（10/2/3）の不一致。文献ベンチと本研究の数値は別表に分離し、Δ は同一 split 内のみで取る。
