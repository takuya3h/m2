# C2 — 混合精度とコンパイルで P→D 側の界面 run を短縮できるか

契約 `T-2026-09-17-amp-compile-timing`。実施 2026-09-17、ホスト `efros`
（RTX A6000 × 2 / driver 595.84 / nvcc 12.9 / torch 2.1.2+cu118）。
**数値はすべて実測である。未測定は UNKNOWN と書く。**

## 1. 問いと答え

問い: 単精度で回している検出側の界面 run を、数値精度を下げる設定と計算グラフの最適化で
短くできるか。短くできるなら主指標は seed 間の散らばりの内側に収まるか。

答え: **短くできる。上限ではなく実測で 1.18〜1.29 倍である。** ただし内訳が二つに分かれる。

- **数値精度は効く。** 行列積の TF32 を許すだけで W1 が 1.182×、W2 が 1.286×。
  自動混合精度（bf16 / fp16）もほぼ同じ 1.17〜1.26× で、こちらは記憶領域が 12.8〜27.1% 減る。
- **結果は変わらない。** 最良条件（tf32）で折り A を 6 epoch 回した主指標は、基準との差が
  best で **0.030σ**、全 epoch を通じて最大 **0.138σ**（σ = 0.004540）。最良 epoch も一致する。
  非有限の損失も跳ねも無い。**速くなったぶんを結果で払っていない。**
- **計算グラフの最適化は使えない。** `torch.compile` は 3 条件とも完走しない。
  実装を改変しない回避（dynamo の eager 退避）でも非数が出る。利用者の判断で除外した。

前契約 `C1` が示したとおり時間の約 85% は transformer の順伝播と逆伝播であり、
そこは**演算そのもの**である。だから演算の精度を落とす手当ては効き、
データ供給やキャッシュの手当ては効かなかった。**効く場所は一貫している。**

## 2. 現行が単精度であること

`scripts/train_t1b.py` に `autocast` `GradScaler` `float16` `bfloat16` `half` `fp16` `bf16`
`torch.compile` `channels_last` は**いずれも 0 件**である。`amp` の 3 件は
`GroupedBatchSampler` / `DataLoader` / `RandomSampler` の語中一致、`dtype` の 3 件は
`np.zeros(NUM_PHASES, dtype=np.float32)`（96・135・199 行）で、いずれも混合精度とは無関係である。

学習ループ（364〜378 行付近）は `model(images, targets)` → `loss.backward()` → `opt.step()` を
素で呼ぶだけで、`import` も `torch` のみ（52 行）である。上流の
`third_party/Relation-DETR/main.py` は `Accelerator(mixed_precision=..., dynamo_backend=...)`
を持つ（107〜115 行、既定は `None`）が、**`train_t1b.py` はその経路を通らない**。

torch の既定では `torch.backends.cuda.matmul.allow_tf32` が False、
`torch.backends.cudnn.allow_tf32` が True である。すなわち**畳み込みは TF32 を使うが
行列積は使っていなかった**。本契約は条件表に `tf32` を加えてこれを測った。

## 3. 条件ごとの実測

同一のバッチ列（要約値で確認）・同一ホスト・同一時刻帯。暖機 10 step を捨て、
**装置の同期を取ってから**計時している。

**W1（入力適合層のみ学習・266,880 param）**

| 条件 | 1 step | 倍率 | 記憶領域の山 | 非有限 | 跳ね |
|---|---:|---:|---:|---:|---:|
| fp32（現行） | 0.4611 s | 1.000× | 14,590,299,648 B | 0 | 0 |
| **tf32** | **0.3902 s** | **1.182×** | 14,589,924,864 B | 0 | 0 |
| bf16 | 0.3927 s | 1.174× | 12,726,704,640 B | 0 | 0 |
| fp16 | 0.3945 s | 1.169× | 12,726,155,776 B | 0 | 0 |
| compile / compile_tf32 / compile_bf16 | **完走しない** | — | — | — | — |

**W2（末端まで学習・25,505,568 param）**

| 条件 | 1 step | 倍率 | 記憶領域の山 |
|---|---:|---:|---:|
| fp32 | 0.5652 s | 1.000× | 13,619,660,288 B |
| **tf32** | **0.4396 s** | **1.286×** | 13,613,707,264 B |
| bf16 | 0.4503 s | 1.255× | 9,929,365,504 B |
| fp16 | 0.4613 s | 1.225× | 9,920,399,360 B |

**W2 のほうが効く。** 学習対象が 95 倍で逆伝播の行列積が増えるためである。

### 計時が壊れていないことの確認

短い測定（40 step）と長い測定（200 step）で倍率が一致する。

| 条件 | 短 | 長 | 差 |
|---|---:|---:|---:|
| tf32 | 1.195× | 1.182× | 1.1% |
| bf16 | 1.204× | 1.174× | 2.5% |
| fp16 | 1.176× | 1.169× | 0.6% |

同期を取らずに測ると速く見える。見かけの短縮は fp32 5.0% / tf32 1.2% / bf16 12.3% / fp16 7.9% と
**条件ごとに違う**ため、同期なしの値で比べると倍率そのものが歪む（bf16 が過大に見える）。

### コンパイルが使えない理由

1. 素の `torch.compile`: `TorchRuntimeError` — `F.one_hot` が記号のままの形を扱えない
   （`third_party/Relation-DETR/models/bricks/set_criterion.py:199`）。画像ごとに物体数が変わるため。
2. 実装を改変しない回避（`suppress_errors`）: eager へ退避して続行するが
   **`ValueError: matrix contains invalid numeric entries`**。Hungarian matcher の費用行列に非数が入る。
3. 解像度が乱択されるため再コンパイルが多発する（graph 59・再コンパイル 17 回を観測）。

利用者の判断により**実装を改変せず除外**した。compile の上乗せ分は UNKNOWN である。

## 4. 主指標の比較

最良条件（tf32）で、基準と**同じ処方・同じ seed・折り A** の run を 1 本、6 epoch 回した。
処方の差分は `--tf32` の 1 つだけで、`config.yaml` で照合して 0 項目である。

seed 間の散らばりの出所: `t1b_filmonly_seed{42,123,456}`（基準と同じ inject=film・trainable=film の
W1 界面 run）。mAP 0.736802 / 0.731410 / 0.725682 で **σ = 0.004540**（pstd）。

| 指標 | 基準 fp32 | tf32 | 差 | abs(差)/σ |
|---|---:|---:|---:|---:|
| init（warm-start の恒等点） | 0.7302938995 | 0.7302930990 | −0.0000008004 | **0.0002** |
| best | 0.7335755045（ep2） | 0.7337119334（ep2） | +0.0001364288 | **0.0301** |
| final（ep5） | 0.7313710102 | 0.7313652919 | −0.0000057183 | **0.0013** |

epoch ごとに並べても、**最大の差は 0.138σ**（ep0）で、すべて散らばりの内側である。

| epoch | −1 | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---:|---:|---:|---:|---:|---:|---:|
| abs(差)/σ | 0.000 | 0.138 | 0.137 | 0.030 | 0.050 | 0.110 | 0.001 |

最良 epoch も ep2 で一致する。**ビット一致ではない**（TF32 は評価にも効くため恒等点でも
−0.0000008 の差が出る）が、差は σ の 1/5000 である。

**数値の異常は無い。** 損失 150 点で非有限 0 件、中央 14.9115 の 3 倍超 0 件（2 倍超が 2 件）。
epoch 別の中央値は 14.640 / 14.306 / 17.147 / 14.097 / 14.594 / 16.550 で発散も単調増大も無い。
なお**基準 run の step 別の損失は記録に存在しない**ため、並べられるのは epoch 別の val mAP までである。

## 6. 前契約の日数の訂正

前契約 `C1` §7 と `RESULT.md` は「縮退なし（K=3・装置 2・**24h/日**）: 153.1〜208.7 日」と書いたが、
**この括弧の前提が誤りである**。153.1〜208.7 は `deadline_sensitivity` 節の値で、
前提は **12h/日・Stage 1 + Tier 1 のみ**である。24h/日・全体なら 84.1〜111.9 日が正しい
（`stage1_plus_tier1.wall_low = 1836.74 h ÷ 12 = 153.06`、`all.wall_low = 2017.53 h ÷ 24 = 84.06`）。
数値は計算器の出力のままで、誤っているのは添えた前提の記述である。

## 7. 採用の可否は利用者が決める

本契約は**採用しない**。`--tf32` と `--amp` は `scripts/train_t1b.py` の任意の引数として足してあり、
**既定（`--tf32` なし・`--amp no`）は従来と同一の経路**である。

判断材料:

- **速さでは tf32 と bf16 に差が無い**（1.182× 対 1.174×）。
- **記憶領域では bf16 が優る**（W1 で 12.8%、W2 で 27.1% 減）。バッチを増やす余地が要るなら bf16。
- **変更の小ささでは tf32 が優る**。記憶の表現を変えず、autocast も尺度調整も要らない。
- 採用すると**既存の単精度 run とは比較の土台が変わる**。分母の再構成が要る。
